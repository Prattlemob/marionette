# M2.4 — Observer role (two-agent streaming) — Design

**Date:** 2026-08-04
**Milestone:** M2.4 (new — ROADMAP.md, Phase 2)
**Prerequisites:** M2.3 (backpressure, coalescing, ping/pong) — merged.
**Sequenced after:** M3.2 (camera smoothing — critical path, in flight).

## Motivating use case

A streamed Minecraft client driven by **two** LLM agents with different
jobs:

- a **brains** agent that decides what to do and drives the body;
- a **commentator** agent that watches the game, reads *stream* chat
  (Twitch/YouTube), and produces TTS for the audience.

The commentator never touches the controls. It reads the game and talks
to viewers.

```
Twitch/YT chat ─┐
                ├─→ harness ─┬─ brains LLM ──(controller)──┐
TTS out ────────┘            │                             ├─→ mod
                             └─ commentator LLM (observer)─┘
```

## Scope

**In scope (this repo, this milestone):** the mod accepts a second,
read-only `role: "observer"` connection alongside the controller, with
independent observation cadence and backpressure per connection, and a
safety model in which observer loss is a non-event.

**Out of scope:** the harness itself — stream-chat ingest, TTS, model
selection, and arbitration between the two agents all live in a separate
out-of-repo project. The mod ships one reference `examples/observer.py`
and nothing more. In-game Minecraft chat (send or receive) is not part of
this use case; M4.6 chat *events* remain where they are in Phase 4.

### MCP is not a transport (D13)

The motivating question was whether Marionette should become an MCP
server. It should not, and this design records why so it is not
re-litigated:

- **Cadence.** The core is a 20 Hz tick-synced stream with latest-wins
  coalescing and set-and-hold actuation. MCP is host-driven
  request/response; it has no notion of a stale frame to drop, and no
  host will pull at tick rate.
- **Event-driven agents.** A commentator must speak unprompted when
  something happens. MCP hosts are turn-driven, so a harness loop is
  required regardless — MCP does not remove it.
- **Dependency footprint.** The MCP Java SDK is Project Reactor +
  Jackson inside a NeoForge client mod, against a jar-in-jar path that
  already drew blood once (D1a dev-classpath addendum).
- **Agent-agnosticism** (CLAUDE.md): MCP is an agent-framework contract.
  Making it the transport excludes scripted, RL, and browser agents that
  D1 chose WebSocket to include.

MCP's legitimate place is **inside the harness**, as the interface
between it and whichever model fills each role — that is where per-role
model swapping is genuinely useful. It never talks to the mod.

## Design

### 1. Protocol changes (spec-first in `protocol/v1.md`)

Additive; **no version bump**. `observer` is already reserved in the v1
capability list and in D7.

- `hello` accepts `role: "observer"`. `role` stays optional, still
  defaulting to `"controller"` — a v1 agent is unaffected.
- Hello reply capabilities gain `"observer": true`.
- Reserved role name added alongside it: `"director"` (a future role
  owning the camera while the controller owns movement). Reserved only —
  rejected as `unsupported_role` until it is designed.
- An observer connection may send `hello` and `configure`. `input`,
  `look`, `release`, and every future actuation message are refused with
  a new **non-fatal** error code `role_forbidden`; the connection stays
  open and no held control changes.
- `configure` is allowed for both roles — a slow per-connection cadence
  is the point of the role.
- New fatal error `observer_attached` (close 1013), mirroring
  `controller_attached`, when the observer cap is full.
- Observers receive `observation` frames and `error` messages. They do
  not receive anything the controller does not.

#### Admission moves after `hello` — deliberate spec correction

v1 states that `controller_attached` is "sent immediately after the
WebSocket upgrade, before any message". That is no longer possible: the
mod cannot know whether a new connection wants `controller` (refuse) or
`observer` (accept) until `hello` arrives. Admission therefore moves to
hello-processing time, and the `controller_attached` error now carries
the offending `input` frame like every other error.

This is treated as a **spec correction with a compatibility note, not a
version bump**, and the judgement is recorded in decisions.md. Rationale:
the spec requires the first message to be `hello`, so for every
conformant agent the error code and close code are unchanged and only the
ordering relative to its own send differs. The old timing was an
implementation detail that leaked into the contract. An agent that waited
for an error *before* sending `hello` was already non-conformant.

**Consequence — hello timeout.** Deferring admission means unauthenticated
connections now occupy the server until they speak. A connection that has
not completed `hello` within a configurable timeout (`bridge.helloTimeoutSeconds`,
default 10) is closed. This is new hardening caused directly by the
change, and it belongs in this milestone.

### 2. Connection model in `BridgeServer`

The blocker is not the role check — it is that per-connection state is
currently per-server:

```
controller / controllerReady   → controller slot + observer list
pendingObservation             → coalescing is per connection
dropped counter                → per connection
lastPongNanos                  → per connection
session rate-divisor override  → per connection
```

Hoist all of it into one `AgentConnection` type (channel,
`ProtocolSession`, role, pending-observation slot, dropped counter,
last-pong timestamp, divisor override). `BridgeServer` then holds an
`AtomicReference<AgentConnection>` for the controller and a bounded
concurrent collection for observers.

- **Observer cap:** `bridge.maxObservers`, default 2 (commentator plus
  one dashboard), range 0–8. `0` disables the role entirely for operators
  who want lockdown. The cap is cheap to raise because each observer
  coalesces independently.
- **Fanout:** `sendObservation` iterates recipients; each applies its own
  writability gate, stash, and counter exactly as M2.3 defined for the
  single controller. A slow observer can only ever drop its own frames.
- **Serialisation:** the v1 frame is identical for all recipients, so it
  is serialised at most once per tick and shared. Noted as a forward
  consideration: once M4.1 lands D2 section masks, recipients with
  different masks need separate serialisation — group by mask then.

### 3. Per-connection cadence

`MarionetteClient` currently holds one session divisor override. It
becomes per connection. The tick loop builds a frame only when at least
one recipient is due, then sends to exactly those that are due.
`MarionetteConfig.observationDueAt(divisor)` already takes a divisor and
needs no change.

**Inbound queue entries must be tagged with their originating
connection.** Two reasons: a `configure` must apply to the right
connection's divisor, and the existing `inbound.clear()` on controller
loss (`BridgeServer.java:288`) must not discard an observer's queued
commands.

### 4. Safety model — the asymmetry is the point

- **Observer loss is not an agent loss.** No release-all, no watchdog
  action, no effect on held controls. The existing agent-loss path stays
  keyed strictly to the controller.
- **Controller loss is unchanged** — release-all within one tick, exactly
  as v1 specifies — and is unaffected by any observer being attached.
- An observer has nothing to release, because it can never actuate.
- **M5.1 inherits this:** the watchdog pings every connection, but a
  missed pong from an observer only drops that observer, while a missed
  pong from the controller triggers release-all. Recorded now so M5.1
  does not have to rediscover it.
- The panic key severs controller actuation. Whether it also disconnects
  observers is an M5.1 question; the default recommendation is **no** —
  a panic should stop the puppet, not blind the stream.

## Roadmap consequences

1. **New M2.4** as specified here. Core tier; prerequisite M2.3;
   sequenced after M3.2 so the critical path to watchable footage is not
   disturbed.
2. **Phase 4 implementation order changes.** The commentator consumes
   *events* — died, took damage, picked up an item, changed dimension —
   far more than inventory or block detail. M4.6 is therefore the
   highest-value item in Phase 4 for this use case, and it currently sits
   last. Rather than renumber (which would churn every cross-reference),
   the Phase 4 header gains an explicit implementation order:
   **M4.1 → M4.6 → M4.2 → M4.3 → M4.4 → M4.5.**
3. **ROADMAP.md assumption 1** ("one agent connection at a time in the
   core spine (D7); observers may be added later behind a capability
   flag") is amended to reflect that observers now exist.

## Testing & verification

**Headless JUnit** (existing style):

- `role: "observer"` accepted; `role: "director"` rejected
  `unsupported_role`.
- Observer sending `input` / `look` / `release` gets `role_forbidden`,
  connection stays open, held controls unchanged.
- Observer accepted while a controller is attached, and vice versa, in
  both connection orders.
- Observer beyond `maxObservers` refused `observer_attached` / 1013;
  `maxObservers = 0` refuses the first.
- `controller_attached` now returned in response to a controller `hello`
  and carries the offending `input` frame.
- Connection that never sends `hello` is closed at the timeout.
- Per-connection independence: a stalled observer accumulates its own
  drop counter while the controller's frames are unaffected.
- Controller loss clears controller-originated inbound commands only, and
  does not disturb an attached observer's session or divisor.

**Live** (scripted client, `Phase1Verify` save) — the asymmetry test is
the one that matters:

1. Controller walks the player; observer reads at `rateDivisor` 40.
2. `kill -9` the observer mid-walk → **the player keeps walking**, and
   the controller sees no disturbance.
3. `kill -9` the controller with the observer still attached → controls
   release within one tick, and the observer stays connected and keeps
   receiving frames.
4. ≥30 min soak with both attached; no drift, leaks, or disconnects.

**`examples/`** (protocol change process, same change):

- New `examples/observer.py` — read-only consumer, low cadence,
  demonstrates `configure` and `role_forbidden`.
- `examples/README.md` documents running a controller and an observer
  side by side.
