# M3.2 — Camera control with stream-quality smoothing — Design

**Milestone:** M3.2 (ROADMAP Phase 3). **Decision:** D5 (experiment-gated —
this spec defines the experiment; the winner gets recorded in
`docs/decisions.md`).

## Goal

Camera movement that looks human on rendered/streamed footage. Three modes:
instant set (existing behavior, unchanged), relative delta, and smoothed
look-at where the mod interpolates yaw/pitch toward a target over time.
Smoothing is evaluated per render frame so footage is smooth at any fps;
state changes (targets, cancellation) happen tick-side only.

## Architecture

### CameraSmoother (new, `control` package)

Owns the continuous camera state while a smoothed pan is active: the target
(absolute angles or world point), the active smoothing model, the per-pan
speed multiplier, and the model's internal state (e.g. angular velocity for
the spring). The D5 candidates sit behind a small internal interface:

```java
interface SmoothingModel {
    /** Advance toward target by dt seconds; returns new (yaw, pitch). */
    Rotation advance(Rotation current, Rotation target, float dt);
    boolean converged(Rotation current, Rotation target);
}
```

Three implementations, ~20 lines each: `DampedSpringModel`,
`ExponentialModel`, `CappedRateModel`. After D5 is judged the losing two are
deleted; the interface stays as documentation of the seam.

### Data flow

- **Tick-side** (existing command drain in `MarionetteClient`):
  - `look` with `mode: "smooth"` sets/replaces the smoother's target and
    starts a pan.
  - `mode: "instant"` and `mode: "delta"` bypass the smoother and write
    rotation directly, canceling any active pan.
  - `release`, disconnect, and world leave cancel the pan; the camera stays
    where it is (no snap-back).
  - World-point targets re-resolve to target angles from the current eye
    position **each tick** while the pan is active, so pointing accuracy
    holds while the player moves. If a re-resolve is degenerate (the eye
    has reached the point), the previous tick's target angles are kept.
- **Render-side** (`RenderFrameEvent.Pre`): if a pan is active and a world
  is loaded, advance the model by the real frame delta and write yaw/pitch
  to the player — the same code path vanilla mouse input uses (vanilla
  applies mouse turns per render frame, not per tick), so body, head, and
  aim stay consistent and footage is per-frame smooth. Client tick and
  render run on the same thread, so there is no cross-thread state.
- **Convergence:** when the model reports converged, the smoother writes
  the exact target angles and the pan ends — "look at X then attack"
  sequencing aims true.
- **Yaw wrapping:** normalized shortest-path at target-set (and point
  re-resolve) time; a pan never goes the long way around. Example: 350°→10°
  pans through 0°.

### Human input during a pan

Mouse deltas still apply (they run in the same frame loop); an active pan
fights them by re-converging. This matches the pre-M5.1 status quo for held
movement keys and will be subsumed by the M5.1 human-override policy. Noted
here deliberately; no mechanism in this milestone.

## Protocol (additive; advertised as the `camera` capability flag)

All three modes ride the existing `look` type via a new optional `mode`
field. `mode` defaults to `"instant"`, so v1 agents are untouched.

### Instant (unchanged wire shape)

```json
{"type": "look", "yaw": 90.0, "pitch": 0.0}
```

### Delta

```json
{"type": "look", "mode": "delta", "yaw": 15.0, "pitch": -5.0}
```

Relative offset in degrees, applied next tick. Multiple deltas arriving in
one tick accumulate. Resulting pitch clamps to ±90.

### Smooth

```json
{"type": "look", "mode": "smooth", "yaw": 90.0, "pitch": 10.0, "speed": 1.5}
{"type": "look", "mode": "smooth", "x": 100.5, "y": 64.0, "z": -20.5}
```

Target is **either** absolute angles **or** a world point (aimed at from
eye height), never both. Optional `speed` is a positive multiplier on the
configured smoothing speed (`1.0` = config default, `2.0` = twice as fast) —
model-agnostic, so the protocol doc survives a future model change.

A new `look` in any mode replaces/cancels whatever pan is active. Success
stays silent (v1 convention). Agents detect convergence from the
observation stream, whose `yaw`/`pitch` already report actual (in-flight)
rotation; a completion *event* waits for the M4.6 event channel.

### Validation (all non-fatal `invalid_field`)

- Unknown `mode` value.
- `mode: "smooth"` with both angles and point, or neither.
- `mode: "smooth"` world point equal to the player's eye position
  (degenerate direction).
- Instant/delta missing `yaw` or `pitch`; non-finite numbers anywhere.
- `speed` ≤ 0 or non-finite.
- `look` in any mode is still discarded while no world is loaded.

### Config

`camera.smoothingSpeed` in `MarionetteConfig`: the winning model's native
speed parameter (degrees/sec for capped-rate; time-constant-derived for
spring/exponential — pinned down when D5 is judged), with documented
default and clamped range. During the experiment only, an additional
`camera.smoothingModel` entry (marked experimental) selects the candidate;
it is deleted when the winner is recorded.

## D5 experiment & verification

**Procedure.** New `examples/look_points.py` drives a five-point pan
sequence (this same script is the milestone's visual verification demo).
For each candidate: select it via the experimental config entry, run the
scripted client (existing quick-play/log-marker setup), capture 60 fps
footage, and log per-frame `[marionette] pan yaw=… pitch=… t=…` lines at
debug verbosity during active pans.

**Numeric pass criteria** (analyzer script over the frame log, per
candidate):

- *No snap:* no frame-to-frame angular step exceeding what the configured
  speed permits for that frame's dt.
- *No overshoot:* the angle never crosses the target and continues beyond
  0.5°.
- *Convergence:* a 90° pan at default speed settles within ~1.5 s with
  final error ≤ 0.1° (also proves convergence fires, since the smoother
  writes exact target angles on convergence).
- *Configurable speed:* the same pan at `speed: 2.0` converges measurably
  faster and still passes the above.

**Visual judgment.** The user reviews the three captures and makes the
final "looks human on stream" call. Winner recorded in `docs/decisions.md`
under D5; losing models and the experimental config entry deleted.

## Testing

- **Unit (pure math):** `SmoothingModel` implementations — convergence,
  no overshoot, shortest-path yaw wrapping, pitch clamping.
- **Unit (state/parsing):** delta accumulation across one tick;
  both-angles-and-point rejection; speed validation; mode defaulting to
  instant; `camera` capability flag in the hello reply (`MessagesTest`).
- **Edge cases:** world leave / disconnect / `release` mid-pan cancels
  without snap-back; instant or delta look mid-pan cancels the pan;
  degenerate look-at target rejected.
- **Visual:** the five-point demo script, plus OBS-captured footage per the
  milestone definition of done.

## Out of scope

- Completion events (M4.6 event channel).
- Human-override policy for camera (M5.1).
- Tracking a moving *entity* (point targets re-aim, but entity-follow
  addressing is future work).
