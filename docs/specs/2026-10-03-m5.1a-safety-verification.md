# M5.1a safety verification — 2026-10-03

Implemented on Minecraft 1.21.8 / NeoForge 21.8.53, Java 21. The wire
contract remains protocol 2 with additive `bridgeSafety` capability and
`overloaded` error. D16 records the owner-approved interim local trust policy;
authentication remains a release gate.

## Transport checks

Final uninstrumented `./gradlew build`: 219 tests passed, zero failed/skipped.
The packaged jar was inspected and contains no temporary verification classes.

Headless tests cover full per-connection command queues, 32-command drains,
priority release at queue capacity, invalidation of already-polled stale work,
observer isolation, missing pongs despite ordinary application traffic,
raw TCP admission limits/timeouts, Origin rejection (including null), bounded
reliable writes including pending event-loop tasks, synchronous-write observation
ordering, stalled real readers, and a 50,000-ping flood from a nonreader.
The ping flood disconnects before the test's five-second watchdog; it cannot bypass
backpressure through Netty's automatic pong replies.

Rendered observer command and reliable-reply floods advanced controller
observations by eight ticks over approximately 0.37 and 0.40 seconds,
respectively. The controller remained attached; no actuation was requested.

## Rendered emergency checks

An isolated survival world and a temporary external verification harness were
used. Protocol actions came from external processes; the harness provisioned
fixtures and sampled actual control, camera, inventory and player state. It is
excluded from the production jar. A window capture confirmed rendered bow-use
and inventory screens, alongside recorded state transitions.

With a one-second pong timeout, the final runtime trials measured:

| Trigger | Release observed |
| --- | --- |
| Controller SIGKILL, all held controls and camera | 9.3 ms |
| Controller SIGSTOP, all held controls and camera | 964.3 ms |
| Panic via registered GLFW key callback, all holds and camera | 3.9 ms |
| Controller SIGKILL during inventory animation | 3.9 ms |
| Panic during inventory animation | 5.5 ms |
| SIGSTOP during inventory animation, already-aged pong lease | 198.4 ms |
| Panic while paused | 7.2 ms |
| SIGKILL after inventory pickup | 4.7 ms |
| Panic after inventory pickup | 7.1 ms |

Timing uses monotonic clocks and samples at rendered-frame boundaries. The
aged-lease inventory test deliberately started the animation near the existing
pong deadline; 198 ms is not a general freeze-detection promise. Earlier
full-lease freeze trials measured up to 1.24 seconds, consistent with the
one-second timeout plus 250 ms check interval and the next responsive frame.
A blocked Minecraft client thread cannot provide a wall-clock guarantee.

Every movement hold, jump/sneak/sprint, attack/use, pending taps/hotbar/look
intent, camera smoothing and inventory animation was checked neutral. Actual
item use also stopped. Already completed world changes are not rolled back.
Inventory cancellation before and after pickup left the destination unchanged;
safe recovery returned the picked-up stack to its source. Killing observers
left the controller's held state intact; observers survived controller loss.

The owner separately focused the rendered client and physically pressed F8
in a camera-only trial. The client logged local panic and controller severance
at 06:08:20 UTC, before the trial's 06:08:57 automatic-cleanup deadline, and
all sampled state was neutral. No synthetic panic input ran in that window.
The initial monitor's immediate log assertion failed; the retained log and owner confirmation establish the
physical event independently. Physical-event latency itself was not measured;
the table's panic measurements use the registered GLFW callback.

## Watchdog default follow-up — 2026-10-03

The owner approved lowering the default `bridge.pongTimeoutSeconds` from 5 to
2 seconds (D16a). Consumer trials at the old default had measured 4.2–5.2 s of
continued walking (about 18–22 blocks) after an agent froze or its network was
blackholed. The wire protocol, capabilities, range and published client are
unchanged. `./gradlew build` passed 222 tests (220 before, plus a config
default test and a headless test). The headless test shows half-lease stalls
survive at the real default and silence is detected within the timeout plus
one interval.

The rendered isolated world was re-measured with the player held walking
forward. The published `marionette-mc==0.1.0a1` was installed hash-pinned from
PyPI, unchanged; its handshake, observation and release smoke passed. External
processes froze the agent (SIGSTOP) or blackholed its bytes through a loopback
proxy. An external sampler recorded controller state, held controls and
position at client-tick boundaries.

| Default | Trials | Failure → disconnect | Disconnect → release | Blocks walked |
| --- | --- | --- | --- | --- |
| 5 s (consumer baseline) | 2 SIGSTOP, 5 blackhole | 4188–5205 ms | 4.9–31.6 ms | 17.7–22.2 |
| 2 s (new default) | 6 SIGSTOP, 6 blackhole | 2022–2386 ms | 1.2–29.2 ms | 8.9–10.4 |
| 1 s (comparison only) | 2 SIGSTOP, 1 blackhole | 836–1146 ms | 2.4–21.3 ms | 3.7–5.0 |

Every release took effect by the first client tick after detection; that tick
ended with forward input false. Half the 2-second trials randomized the
failure's ping phase.

Healthy agents injected blocking event-loop pauses (sleep or forced garbage
collection) of 0.05–1 s every 2–6 s:

- At 2 s, the agent stayed connected for 154 s through 31 pauses, the longest
  979 ms, with no disconnect.
- At 1 s, the same profile was dropped with 1008 `pong timeout` after 53 s and
  60 s in two runs.

| Single pause | At 2 s, dropped | At 1 s, dropped |
| --- | --- | --- |
| 0.5 s | — | 0/3 |
| 0.75 s | — | 0/3 |
| 0.9 s | — | 1/3 |
| 1.0 s | 0/3 | 1/3 |
| 1.5 s | 0/3 | — |
| 1.9 s | 1/3 | — |
| 2.6 s | 2/2 | — |

A pause shorter than the timeout minus one ping interval is always tolerated,
and some slightly longer pauses survive depending on ping phase. These are
single-machine measurements, not universal deadlines.

## Panic latch follow-up — 2026-10-04

An end-to-end consumer check found that panic severed the controller within a
millisecond, but a reconnecting agent drove the player again 0.4–2.6 s after
each of 25 physical presses. The owner decided that panic latches controller
admission off until a separate re-arm key clears it (D16b). The contract is in
protocol/v1.md (Emergency release): a latched refusal is error `panic_latched`
plus close 1008 `panic_latched`. The sever is unchanged (close 1008
`local panic`). The `panicLatch` capability is additive.

`./gradlew build` passed 229 tests (222 before). New headless tests cover: the
distinct sever and refusal signals; observers admitted and kept while latched;
25 repeated panics staying latched; re-arm clearing the latch without
admitting or replaying anything; the latch surviving the world-exit sever; 40
hellos racing a panic, each either severed or refused, never left attached;
and the error-code and session refusal mapping.

The rendered isolated world was driven by external processes using the
published `marionette-mc==0.1.0a1`, installed hash-pinned from PyPI and used
unchanged. A temporary harness, excluded from the jar, injected F8/F9 through
the registered GLFW key callback and sampled state at 0.25 ms and at
client-tick boundaries.

| Step | Result |
| --- | --- |
| Agent forward walk, then synthetic F8 | Latch engaged and controller invalid at 1.3 ms; forward and applier released at 1.6 ms, before the next client tick (41.5 ms), which ended with forward input false |
| Agent's view of the sever | Close 1008 `local panic` at 3.7 ms |
| Reconnect every ~0.4 s while latched | 28 attempts over 10.9 s, all `ServerError` `panic_latched`, refused 1.5–2.8 ms after connecting; z range 0.0000 blocks over 217 ticks; no forward input |
| Five more synthetic F8 presses | Latch stayed engaged; a controller attempt after each press was refused |
| World exit, title screen, rejoin | Refused on the title screen and after rejoin; "still disabled" notice on rejoin |
| Synthetic F9 (re-arm) | Latch cleared 0.2 ms later; for the next second there was no input and no movement |
| Controller after re-arm | Admitted; a bounded 0.5 s forward hold, then release |
| Observer throughout | One observer stayed attached for the whole run (394 frames, no disconnect) |
| Client restarted while latched | Started unlatched; a controller was admitted |
| Rebinding | With panic on F7 and re-arm on F6, F8/F9 did nothing and F7/F6 worked; restored to F8/F9 |

Screenshots confirmed both mappings in Controls → Marionette, before and after
rebinding, and the disabled, still-disabled and re-enabled toasts. No physical
key press or jump input was used. Physical-press latency was not re-measured.
