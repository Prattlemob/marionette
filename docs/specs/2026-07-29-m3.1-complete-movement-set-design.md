# M3.1 — Complete Movement Set: Design

**Date:** 2026-07-29
**Milestone:** M3.1 (ROADMAP.md, Phase 3)
**Status:** Approved

## Context

Most of M3.1 already exists: `forward`, `back`, `left`, `right`, `jump`,
`sneak`, and `sprint` are live end-to-end as held booleans — protocol v1
`input` message → `MessageParser` → `ControlState` → the D4
`KeyboardInputMixin`, which OR-merges agent controls into vanilla
`keyPresses`. Because the merge happens upstream of vanilla's own logic,
sneak speed caps, sprint gating, and sneak edge-stopping behave exactly
like real key input with no extra code.

What remains:

1. Settle the open movement-axes decision (docs/decisions.md).
2. Spec and implement one-shot taps — `jump` only in this milestone.
3. A demo script proving every control and the DoD combinations.
4. Record the decision; tick the roadmap boxes.

## Decisions

**Movement axes are boolean (settled).** Key-like booleans stay the wire
format. Smoothness was the deciding concern and booleans do not hurt it:
vanilla physics already applies acceleration/friction ramps to boolean
input, and curved paths come from camera yaw (M3.2 smoothing), not the
movement axes. Analog floats would add speed granularity — not
smoothness — while bypassing the mixin's vanilla-parity guarantees. If a
real use case appears, analog arrives later as an additive message with
a capability flag; nothing in v1 changes shape. Recorded in
docs/decisions.md.

**Tap shape: a `tap` array on the `input` message.** Taps ride the
existing message, combine with held fields in one atomic update (e.g.
sprint-jump), and the array extends to `attack`/`use` in M3.3 with no
new message types.

## Protocol changes (spec-first; additive; protocol stays v1)

Changes land in `protocol/v1.md` before implementation, per
`protocol/README.md`.

### `input.tap`

```json
{"type": "input", "forward": true, "sprint": true, "tap": ["jump"]}
```

- Optional array of control names. v1 accepts only `"jump"`; the spec
  notes the value set extends in M3.3 (`attack`, `use`).
- **Semantics:** each tapped control is pressed for exactly one client
  tick on the next tick, then auto-releases. The agent never times a
  press/release round-trip.
- Tapping a control that is already held is a no-op — the control stays
  held; a tap never releases anything.
- Duplicate entries in one array collapse. Multiple `tap` messages
  arriving between ticks collapse to a single one-tick press.
- **Validation:** a non-array `tap`, a non-string entry, or an unknown
  name is a non-fatal `invalid_field` error and the message is not
  applied (matching existing `input` validation conventions).
- While no world is loaded, taps are discarded along with the rest of
  `input` (existing rule).

### `release` and safety

`release` — and every safety-triggered release-all (disconnect, error,
world leave) — clears pending taps along with held controls.

### Capability flag

The `hello` reply capabilities gain `"tap": true`. Agents
feature-detect per `protocol/README.md`; no version bump (additive).

## Implementation

- **`ControlState`** (stays pure-data, no Minecraft imports): a
  pending-tap set — `tap(control)`, `consumeTaps()`, cleared by
  `releaseAll()`. Tappable controls are an enum so M3.3 adds values,
  not mechanisms.
- **`KeyboardInputMixin`**: jump merge becomes `held || tapped`. Taps
  are consumed exactly once per `KeyboardInput.tick` pass, so the
  one-tick guarantee holds regardless of when messages arrive.
- **Parser / `AgentCommand.InputUpdate`**: carry the tap set through
  the existing marshal-to-tick path. No threading changes — taps ride
  the same queue as held fields and are only touched on the client tick
  thread.
- Held sprint/sneak/jump need no code changes.

## Testing & verification

- **Unit tests**, in the existing suites:
  - `MessageParserTest`: `tap` array parsing; rejection of non-arrays,
    non-string entries, unknown names.
  - `ControlStateTest`: tap consumed exactly once; `releaseAll()`
    clears pending taps; tap-while-held leaves the hold intact.
  - `ProtocolSessionTest`: `tap` capability advertised in the `hello`
    reply.
- **Demo:** new `examples/full_movement.py` exercising each control,
  then the combinations from the roadmap DoD — sprint-jump run,
  sneak-walk to a block edge without falling (vanilla edge-stop through
  the mixin), hold-jump bunny-hop vs. a single tap-jump. Verified in a
  rendered client via the established scripted-verification flow
  (quick-play join + log markers).
- `./gradlew build` green.

## Out of scope

- Camera smoothing and look modes (M3.2).
- Attack/use taps and hotbar (M3.3) — only the tap *shape* is fixed
  here.
- Analog movement axes (reserved, additive-later).
- Any protocol version bump.
