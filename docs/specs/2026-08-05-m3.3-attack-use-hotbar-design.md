# M3.3 — Attack / Use / Hotbar: Design

**Date:** 2026-08-05
**Milestone:** M3.3 (ROADMAP.md, Phase 3)
**Status:** Approved

## Context

M3.3 adds the interaction primitives: attack and use as both held
controls (mining, eating, bow draw) and one-shot clicks, plus hotbar
slot selection. The wire shape is half-committed already: `protocol/v1.md`
promises that `"attack"` and `"use"` join the `input.tap` array in M3.3,
and holds follow the `input` boolean convention from M3.1.

The injection point differs from movement. Movement lives in
`KeyboardInput.tick()`, where the D4 mixin OR-merges agent state.
Attack, use, and hotbar live in `Minecraft.handleKeybinds()`:
`consumeClick()` loops fire `startAttack()` / `startUseItem()`,
`isDown()` drives held mining (`continueAttack`) and held use, and
hotbar selection calls `Inventory.setSelectedSlot(0–8)`. Routing agent
intent through that path gives the roadmap's "respect vanilla timing"
item — attack cooldown, `missTime`, `rightClickDelay`, use ticks — for
free, because vanilla itself runs the timing.

Three facts from the 1.21.8 decompile
(`build/moddev/artifacts/neoforge-21.8.53-sources.jar`) shape the
design:

1. **`handleKeybinds()` runs only while no screen and no overlay is
   open** (`Minecraft.tick`). Agent attack/use is therefore naturally
   inert while a menu is up — unlike movement, which deliberately
   continues through GUIs (D4).
2. **Held-attack mining requires `mouseHandler.isMouseGrabbed()`**,
   which is false while the window is unfocused. The mod deliberately
   keeps unfocused clients running (`client.suppressPauseOnLostFocus`,
   M2.2), so without a fix an alt-tab would silently stop agent mining.
3. **While a screen is open, vanilla sets `missTime = 10000` every
   tick**, and it decays by 1 per tick. Humans never notice: opening a
   screen releases every key (`setScreen` → `KeyMapping.releaseAll()`),
   so `continueAttack(false)` resets `missTime` to 0 on close. An agent
   hold that "resumed" after a screen closed would instead keep
   `missTime` huge and stall mining for ~8 minutes.

## Decisions

**Injection: a second scoped mixin, on `Minecraft.handleKeybinds()`.**
Three `@Redirect`s, all scoped to that one method, OR agent intent into
the values vanilla reads — the same manipulate-meaning-not-key-state
philosophy that won D4:

- `KeyMapping.isDown()` → vanilla `||` agent hold (identity-checked
  against `options.keyAttack` / `options.keyUse`; every other mapping
  passes through untouched).
- `KeyMapping.consumeClick()` → vanilla `||` consume-once agent tap.
- `MouseHandler.isMouseGrabbed()` → vanilla `||` agent attack held
  (fixes fact 2; the call gates only `continueAttack`'s argument).

Rejected: KeyMapping forcing (`click()`/`setDown()`) — held mining dies
unfocused, and `release()` would stomp a genuinely held human button;
direct invoker calls to `startAttack()`/`startUseItem()` — duplicates
vanilla's `missTime`/`rightClickDelay`/`isUsingItem` orchestration,
which would need re-verification every Minecraft bump.

**Screen-open rule: opening a screen releases agent attack/use.** Fact 3
makes "holds resume on close" unimplementable without fighting vanilla,
and vanilla itself releases held keys on screen open — so the agent's
holds mirror that. Opening any screen clears the attack/use holds and
any pending attack/use taps; the agent re-asserts them after the screen
closes. Movement holds are untouched (their continue-through-GUI
behavior is D4-recorded and `missTime` does not affect them). Pending
attack/use taps that no `handleKeybinds` run consumed by end of tick
are dropped, never queued — a stale click must not fire when a menu
closes seconds later.

**Hotbar rides `input` as a one-shot intent.** `{"type": "input",
"hotbar": 3}` — optional integer 0–8, omitted-unchanged like every
other `input` field, atomic with holds and taps (select the pickaxe and
start mining in one frame). Slot selection is world state, not a held
control: `release` and the safety release-all do **not** restore the
previous slot, exactly as the camera stays where a released pan left
it. Applied via `Inventory.setSelectedSlot` only while no screen is
open; with a screen open the intent is dropped (vanilla number keys
mean hover-swap there, not slot select — plain re-selection is not
vanilla-reachable, and M3.4 owns in-menu slot operations).

**Hold rising edge synthesizes one click.** A vanilla button press both
sets `isDown` and registers a click; `isDown` alone never lands the
first swing. `ControlState.setAttack(true)` (and `setUse(true)`) when
the control was previously up therefore enqueues the matching tap
internally. Re-sending `attack: true` while already held is no edge and
taps nothing.

**Capability flag: `interact`.** Advertised in the `hello` reply,
covering the `attack`/`use` fields (held + tap) and `hotbar`. Additive;
protocol stays v1.

## Protocol changes (spec-first; additive; protocol stays v1)

Changes land in `protocol/v1.md` before implementation, per
`protocol/README.md`.

### `input` additions

```json
{"type": "input", "hotbar": 0, "attack": true}
{"type": "input", "use": true}
{"type": "input", "tap": ["use"]}
```

- `attack`, `use` — optional booleans, set-and-hold, omitted-unchanged.
- `tap` — now accepts `"attack"` and `"use"` alongside `"jump"`.
  Existing tap semantics unchanged: duplicates collapse, a tap never
  releases anything, tapping a held control is a no-op.
- `hotbar` — optional integer 0–8 selecting the hotbar slot on the next
  tick. Out-of-range or non-integer values are a non-fatal
  `invalid_field` error and the whole message is not applied (the same
  rule as a bad `tap` entry).

### Documented semantics

- Held `attack` mines blocks continuously and survives an unfocused
  window. It does **not** repeat entity hits: vanilla swings only on
  clicks, so agents tap `attack` per swing to fight. Tap cadence is the
  agent's problem; vanilla attack cooldown applies either way.
- Held `use` behaves like a held right mouse button: eating, bow draw,
  block placement at vanilla's 4-tick repeat.
- Opening any screen (inventory, chest, pause) releases agent
  `attack`/`use` holds and drops pending `attack`/`use` taps and
  `hotbar` intents. The agent re-asserts holds after the screen closes.
  Movement holds are unaffected.
- `release` and every safety-triggered release-all clear the new holds
  and pending taps; the selected hotbar slot stays.

## Implementation

### `ControlState`

- `attack` / `use` held flags, included in `anyHeld()` and
  `releaseAll()`; setters enqueue the matching tap on a rising edge.
- Public `tap(ATTACK)` / `tap(USE)` while that control is already held
  is ignored. For `jump` the no-op rule is automatic (the OR-merge makes
  a tap of a held control invisible), but an attack/use tap becomes a
  consumed click that would fire a real extra swing — so the held-tap
  no-op must be enforced here. The internal edge tap enqueues as part of
  the rising-edge transition and is unaffected.
- `TapControl` gains `ATTACK` and `USE`; wire names come free from the
  enum.
- Tap consumption becomes per-control: `boolean consumeTap(TapControl)`
  replaces wholesale `consumeTaps()`. `KeyboardInputMixin` consumes only
  `JUMP`; the new mixin consumes `ATTACK`/`USE`. Consume-once semantics
  bound the vanilla `while (consumeClick())` loops.
- A consumed one-shot hotbar intent (the `Look` pattern).
- `releaseInteractions()`: clears attack/use holds, their pending taps,
  and the hotbar intent — the screen-open rule.

### `MinecraftInteractionMixin` (new; `@Mixin(Minecraft.class)`)

The three `@Redirect`s above, each scoped to `handleKeybinds()`. Null
`MixinInputApplier.activeState()` → pure vanilla. Everything downstream
— `startAttack`, `continueAttack`, `startUseItem`, NeoForge's
`onClickInput` hooks — runs untouched, so other mods observe agent
clicks exactly like human ones. Taps drained while `isUsingItem` are
discarded by vanilla's own drain loops, matching clicks mid-eating.

A `setScreen` return hook also releases interactions if the resulting
screen is non-null. This handles screens opened within `handleKeybinds`
after tick-pre, respecting NeoForge's screen-event cancellation/replacement.

### `MessageParser` / `Messages`

- `attack`, `use` via the existing optional-boolean helper; `hotbar` via
  the existing ranged-int helper (0–8).
- `AgentCommand.InputUpdate` carries the two new booleans and the
  hotbar Integer.
- `Messages.helloReply` advertises `interact: true`.

### `MarionetteClient`

- Apply: set the new holds (edge taps fire inside `ControlState`),
  queue the hotbar intent.
- Tick pre: if a screen is open, call `releaseInteractions()`;
  otherwise consume the hotbar intent into
  `player.getInventory().setSelectedSlot(n)`.
- Tick post (`ClientTickEvent.Post` fires after `handleKeybinds` in
  `Minecraft.tick`): drop attack/use taps that were not consumed this
  tick — the one-tick tap lifetime.

### Safety

Unchanged in shape. Release-all clears the new holds and taps; with the
applier released the mixin is inert, vanilla sees the real (released)
key state, and its own `releaseUsingItem` / `stopDestroyBlock` fire on
the next `handleKeybinds`. Controller loss still releases everything
within one tick.

## Edge cases

- **Tap while using an item:** drained without effect, like a vanilla
  click mid-eating.
- **Held attack over an entity:** one swing at the rising edge, then
  nothing — vanilla parity; agents tap to fight.
- **Spectator mode:** `setSelectedSlot` runs its plain path; the
  spectator hotbar menu is not driven. Out of scope for v1; documented.
- **Death/respawn, world leave:** existing release-all paths already
  clear the new state (`releaseAll` covers it).
- **`tap: ["attack"]` in the same message as `attack: true`:** the
  hold's edge click and the tap collapse into one click.

## Testing & verification

- **Unit:** `ControlState` (edge taps, per-control consumption, hotbar
  intent, `releaseInteractions`, `releaseAll` coverage of new state);
  `MessageParser` (new fields, validation, tap names); `Messages`
  (`interact` flag). Mixin bodies stay thin identity checks, per
  project pattern.
- **Live (DoD, Phase1Verify save, survival for real mining):** script
  selects the pickaxe slot, holds `attack` to mine a block to
  completion, one-shot `use` places a block, holds `use` to eat food —
  rendered, no keyboard. Plus an alt-tab mid-mine check proving the
  `isMouseGrabbed` fix, and a screen-open check proving the release
  rule.
- **Demo:** `examples/interact.py`, verified against the running
  client; log markers per the established verification recipe.

## Verification record (2026-10-02)

Integrated the existing M3.3 branch with the shared agent guidance and Netty
dependency fix. Review also corrected two timing issues: jump taps must be
consumed even when a held jump short-circuits the input merge, and screen-open
release must happen within `setScreen`, not only at the following tick-pre.

The rendered `runClientDemo` loaded the mixins and joined an isolated copy of
`Phase1Verify`. Temporary client instrumentation provisioned a survival-world
fixture and sampled actual client state. An external WebSocket driver sent the
normal protocol commands; the instrumentation did not implement the actions.
Original development worlds were untouched, and the harness is not part of the
mod or its packaged artifact.

| Check | Observed result |
| --- | --- |
| Handshake and validation | `interact: true`; slot 9 rejected as `invalid_field` |
| Held mining, mouse ungrabbed | Slot 0 selected; targeted stone became air |
| One-shot placement | Slot 1 selected; target became dirt; stack decreased 16 → 15 |
| Held eating | Slot 2 selected; cooked beef decreased 8 → 7; hunger increased 10 → 18 |
| Explicit release | Held use cleared |
| Screen open | Attack/use cleared immediately; in-screen slot/tap/hold commands discarded |
| Screen close | Neither hold resumed without reassertion |
| Controller disconnect | Input applier became inactive and attack cleared; player remained alive |

The fixture disabled mob spawning and applied resistance to isolate input
behavior from ambient damage. Screens were opened through Minecraft's normal
`setScreen` path; the ungrabbed check used `MouseHandler.releaseMouse`.
These checks establish runtime effects, not a human judgment of animation
quality or an actual OS focus transition. Visual review and physical alt-tab
remain on the roadmap. No dedicated-server launch was performed for this change.

Final uninstrumented `./gradlew build`: 174 tests passed, none failed or skipped.
The packaged jar was checked to exclude the temporary verification harness.
