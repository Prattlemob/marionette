# Marionette protocol — version 2

> **Status: current (protocol 2; canonical path retained).** Supersedes [v0-draft.md](v0-draft.md). Versioning and
> change process are defined in [README.md](README.md).

## Migration from protocol 1

Only protocol 2 is accepted. Offer `versions: [2]`; move reads of `x`, `y`,
`z`, `yaw`, and `pitch` from the frame root to `frame.player`. `tick` stays
at the root. Commands and inventory results retain their existing shapes.

## Transport

- WebSocket, **text frames only**, one JSON object per frame.
- Endpoint: `ws://127.0.0.1:24680/` (loopback only; port and bind address
  configurable per M2.2). The address is resolved and validated once.
- HTTP requests carrying any Origin header, including `null`, receive HTTP
  403 before upgrade. Development clients must be native and omit Origin.
  Local processes are trusted without authentication; authentication remains
  a release gate (D16 in docs/decisions.md).
- A binary frame is a protocol violation: the connection closes with
  WebSocket close code `1003` (unsupported data), and any text frames
  already in flight behind it are discarded unprocessed.
- Messages over the frame-size limit (64 KiB) close the connection with
  close code `1009` (message too big).
- One **controller** connection at a time, plus up to `bridge.maxObservers`
  (default 2) read-only **observer** connections (see Handshake). Each
  connection has its own observation cadence and its own backpressure
  state: a slow reader only ever drops its own frames.
- A connection that has not completed the `hello` handshake within
  `bridge.helloTimeoutSeconds` (default 10) is closed with WebSocket close
  code `1002` and no error frame.
- **Liveness (`bridgeSafety`):** ping cadence is at most one second (or a
  quarter of the configured timeout). `bridge.pongTimeoutSeconds` defaults
  to 5 seconds, range 1–60, restart required. A session that supplies no
  pong by that deadline closes with 1008 (`pong timeout`); other traffic
  does not renew the deadline. Timing starts when hello is admitted.
- **Limits (`bridgeSafety`):** at most 128 queued commands per connection;
  one additional priority release slot. A full command queue closes only the
  offending connection with 1013 (`overloaded`) and a best-effort `overloaded`
  error. Each tick starts at most 32 commands and stops starting commands
  after 2 ms; a running vanilla action cannot be preempted. Connections are
  serviced round-robin. Release clears that controller's earlier queued work
  and precedes ordinary commands. Disconnect/panic invalidate queued work.
- Reliable text writes have a 256 KiB per-connection UTF-8 byte budget,
  including writes awaiting the network event loop; individual replies are
  limited to 128 KiB. Exceeding either limit disconnects with 1013. Replies
  never coalesce; on disconnect outstanding requests have unknown outcomes
  and must not be replayed blindly. A saturated channel may close without
  delivering its final error/close frame. Close flushing is limited to 250 ms.
- At most 8 connections may wait for HTTP upgrade/hello, with the hello
  timeout measured from TCP accept (including incomplete HTTP). Excess TCP
  connections are closed before upgrade. Established role limits are separate.
- Observations retain one latest stashed frame and at most one scheduled stash flush per
  connection, with a 128 KiB frame cap and the shared 256 KiB outbound budget.
  Observation overload coalesces; reliable overload disconnects. Automatic
  pong replies also disconnect the offending peer on channel unwritability;
  control-frame floods cannot bypass output backpressure.
- **Shutdown:** when the game quits, the mod closes the connection with
  close code `1001` (going away) after releasing all controls.

## Envelope

Every message, in both directions, is a flat JSON object. Two top-level
keys are reserved:

- `type` — **required** string. Determines every other field's meaning.
  An unrecognized `type` from the agent is an `unknown_type` error.
- `id` — optional, a JSON string or number. Echoed verbatim in any reply
  the message causes (`error`, `hello`, or `inventory_result`). Any other JSON
  type for `id` is an `invalid_field` error. The mod never generates ids
  of its own in v2; replies without a causing id omit the field.

Unknown non-reserved fields are ignored (forward compatibility: additive
fields never break old agents). All other unknown input is an error.

## Handshake

The first message on a connection MUST be `hello`:

```json
{"type": "hello", "versions": [2], "role": "controller"}
```

- `versions` — required non-empty array of integers: every protocol
  version the agent speaks. The mod selects the highest version both
  sides support.
- `role` — optional string, default `"controller"`. Accepted values:
  `"controller"` (drives the player; at most one attached at a time) and
  `"observer"` (read-only observation stream — commentator agents,
  dashboards; capped by config). `"director"` (camera ownership split
  from movement) is a reserved name: it is rejected as
  `unsupported_role` until designed. An observer session may send only
  `hello` and `configure`; every other message is refused with a
  non-fatal `role_forbidden` error.

`sections` may also be supplied in hello, with the same validation and semantics
as configure below. It takes effect before the first observation.

On success the mod replies, and the session is active:

```json
{"type": "hello", "version": 2, "capabilities": {"configure": true, "tap": true, "camera": true, "observer": true, "interact": true, "inventory": true, "inventoryAnimation": true, "playerState": true, "bridgeSafety": true}, "mod": "0.1.0"}
```

- `version` — the selected protocol version.
- `capabilities` — feature flags. **Absent flag = unsupported**; agents
  feature-detect with a truthy check, never by version comparison.
  v2 flags: `configure` (the `configure` message below), `tap` (the
  `input.tap` one-shot field), `camera` (the `look` delta and smooth
  modes), `observer` (the mod accepts observer connections), `interact`
  (the `input` `attack`/`use` fields — held and tap — and `hotbar`).
  `inventory` advertises the controller-only inventory request/result API below.
  `inventoryAnimation` supports its opt-in `animated` field.
  `bridgeSafety` advertises the bounded transport and emergency behavior above.
  `playerState` advertises the player section and `sections` selection.
  Reserved names: `baritone`, `server`, `vision`.
- `mod` — informational mod version (semver, independent of the protocol
  version).

### Handshake rejection

Fatal rejections send an `error` message as the final text frame, then
close with the listed WebSocket close code:

| Condition | `code` | WS close |
|---|---|---|
| First message is not a valid `hello` (wrong type, malformed JSON, bad field) | `hello_required` / `invalid_json` / `invalid_field` / `unknown_type` | 1002 |
| No shared protocol version (error carries `supported`: array of versions the mod speaks) | `unsupported_version` | 1002 |
| `role` present but not `"controller"` or `"observer"` | `unsupported_role` | 1002 |
| A controller is already attached (in reply to a `controller` hello) | `controller_attached` | 1013 |
| The observer limit is reached (in reply to an `observer` hello) | `observer_attached` | 1013 |

During the handshake **every** error is fatal. A repeated `hello` on an
already-active session is the one exception by position: it arrives after
the handshake, and is a non-fatal `unexpected_hello` error (connection
stays open, held controls untouched).

## Agent → mod messages (after hello)

All commands accept an optional `id` (see Envelope). Except for `inventory`, success is silent:
commands produce no reply; the next observation shows their effect.
While no world is loaded, `input`, `look`, and `release` are discarded.

### input — set-and-hold controls, one-shot taps, hotbar select

```json
{"type": "input", "forward": true, "sprint": true, "tap": ["jump"]}
{"type": "input", "hotbar": 0, "attack": true}
{"type": "input", "use": true}
{"type": "input", "tap": ["use"]}
```

Held fields (all optional booleans): `forward`, `back`, `left`,
`right`, `jump`, `sneak`, `sprint`, `attack`, `use`. **Omitted fields
are unchanged.** Held values persist until a later message changes them
(set-and-hold). `attack`/`use` and `hotbar` are advertised together as
the `interact` capability flag.

- Held `attack` behaves like a held left mouse button: it mines the
  targeted block continuously (and keeps mining while the window is
  unfocused). It does **not** repeat entity hits — vanilla swings only
  on clicks — so agents tap `attack` once per swing to fight; the
  vanilla attack cooldown applies either way.
- Held `use` behaves like a held right mouse button: eating, bow draw,
  block placement at vanilla's repeat rate.
- Starting to hold `attack` or `use` counts as one click (a vanilla
  press both holds the button and clicks it); re-sending `true` while
  already held clicks nothing.

`tap` — optional array of control names, each pressed for **exactly one
client tick** on the next tick, then auto-released; the agent never
times a press/release round-trip. v2 accepts `"jump"`, `"attack"`, and
`"use"`. Advertised as the `tap` capability flag. Semantics:

- Tapping a control that is already held is a no-op: the control stays
  held. A tap never releases anything.
- Duplicate entries in one array collapse; multiple `tap` messages
  arriving between ticks collapse to a single one-tick press.
- An `attack`/`use` tap the game could not consume on its tick (a
  screen was open) is dropped, never queued — a stale click must not
  fire when a menu closes later.
- A non-array `tap`, a non-string entry, or an unknown name is a
  non-fatal `invalid_field` error; the whole message is not applied.
- `release` — and every safety-triggered release-all — clears pending
  taps along with held controls.

`hotbar` — optional integer 0–8: select that hotbar slot on the next
tick. Out-of-range or non-integer values are a non-fatal
`invalid_field` error and the whole message is not applied. Slot
selection is world state, not a held control: `release` and the safety
release-all do **not** restore the previous slot. While a screen is
open the select is dropped (vanilla number keys mean hover-swap there,
not slot select).

**Screens:** opening any screen (inventory, chest, pause menu) releases
agent `attack`/`use` holds and drops pending `attack`/`use` taps and
`hotbar` selects — mirroring vanilla, which releases every key when a
screen opens. Holds do not resume when the screen closes; the agent
re-asserts them. Movement holds are unaffected (they deliberately
continue through GUIs).

### inventory — menu-addressed inventory actions

Advertised as `inventory`. Controller-only (including `inspect`); observers
remain read-only stream consumers. Each request gets one reliable
`inventory_result` or non-fatal `error`, echoing its optional `id`.
Unlike movement, requests without a live player fail with `inventory_unavailable`.

```json
{"type":"inventory","id":"open","op":"open"}
{"type":"inventory","id":"read","op":"inspect"}
{"type":"inventory","id":"move","op":"move","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3},"from":"main.0","to":"hotbar.0"}
{"type":"inventory","op":"swap","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3},"from":"main.1","hotbar":1}
{"type":"inventory","op":"equip","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3},"from":"main.2"}
{"type":"inventory","op":"drop","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3},"from":"hotbar.0","all":false}
{"type":"inventory","op":"close","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3}}
```

- `open` opens the survival inventory only when no screen is open and the
  player's inventory is the active menu. It never replaces another screen.
- `inspect` returns the current visible menu and its slots, or `menu: null`
  if no container screen is open. This on-demand descriptor supports M3.4;
  periodic inventory observation is still M4.2.
- All other operations require `menu` with `type` (string), `containerId`
  and `stateId` (non-negative integers), copied from the latest result.
  They must match the active screen's actual menu at application time;
  mismatches fail with `stale_menu`. InventoryMenu has no registered type:
  `minecraft:inventory` is its protocol name. Other types use registry ids.
- Slot references (`from`, `to`) are either a non-negative menu slot index
  or a player alias: `hotbar.0`–`hotbar.8`, `main.0`–`main.26`,
  `armor.head`, `armor.chest`, `armor.legs`, `armor.feet`, `offhand`.
  Aliases resolve by backing player inventory and container slot, never by
  assuming where a menu puts player slots. An alias absent from that menu
  fails with `inventory_impossible`.
- `move` moves the entire source stack into an empty or matching destination.
  The entire stack must fit; incompatible/full destinations fail without
  clicking. Source and destination must differ.
- `swap` swaps the source stack with hotbar slot `hotbar` (integer 0–8).
  Both directions must satisfy slot pickup, placement and capacity rules.
- `equip` moves a single armor item into its matching, empty armor slot.
  That armor slot must exist in the current menu. Occupied armor is not replaced.
- `drop` drops one item, or the whole stack with `all: true` (default false).
- `close` uses vanilla container close, including its server notification.
  A nonempty cursor is refused rather than implicitly returning/dropping items.

All mutations run on the client tick through vanilla inventory clicks; they
never directly edit inventory stacks. Empty sources, occupied cursor, forbidden
slots, invalid destinations, and unsupported operations fail before any clicks
with `inventory_impossible`. No open menu, dead/spectator player, creative mode,
or unrelated screen fails with `inventory_unavailable`. Supported menus are
player inventory and vanilla chest/barrel, hopper, dispenser/dropper, and
shulker box menus. Other menu implementations fail with `inventory_unavailable`;
the wire addressing remains generic. Crafting input/result slots and bundle
click behavior are outside this milestone and refused.

Results describe **client prediction**, not a server acknowledgment. Vanilla
server synchronization remains authoritative and may correct a predicted move.
The state id detects server updates, not every local edit; it is not an atomic
transaction or a permanent menu identifier. Re-inspect after synchronization
before dependent commands; do not pipeline operations based on an old snapshot.
By default all clicks for one action execute in the same tick. Unexpected vanilla click behavior stops the sequence
with `inventory_impossible`; any carried item remains visible for recovery,
never discarded by the mod.

#### Visible inventory interactions

`animated: true` on `move`, `equip`, `swap`, or `drop` enables the
`inventoryAnimation` capability. Default is false; non-boolean values are
`invalid_field`. Open/inspect/close accept the field but perform no animation.

```json
{"type":"inventory","id":"move","op":"move","animated":true,"menu":{"type":"minecraft:inventory","containerId":0,"stateId":3},"from":"main.0","to":"hotbar.0"}
```

The client draws an agent cursor over the actual inventory screen. It moves
smoothly to the source, pauses to click, and, for move/equip, carries the actual
vanilla cursor stack to the destination before placing it. Travel takes roughly
0.2–0.45 seconds per leg plus a short click pause. Swap uses the vanilla
number-key operation at the source; drop uses vanilla throw at the source.
These have one click cue rather than a carried-stack leg. The OS pointer is
not moved. Human mouse/keyboard input retains its own pointer and control.

Only one animated action may run at a time. Further mutations (including
open/close) fail with `inventory_busy`; inspect remains available. The result
arrives after the final click and is still a client prediction. No unbounded
animation queue exists. Await the result before sending a dependent command.

Each click revalidates the same player, screen, menu, slot contents and cursor.
`release`, controller loss, world exit, menu/screen replacement, or human
mouse press/scroll/key press cancels remaining clicks. Changed contents also
cancel the action. Cancellation reports `inventory_cancelled` if the requesting
connection remains available. A picked-up stack is returned through a vanilla
click only when the same live menu remains open, the carried stack is exactly
the one picked up, and the original source is empty and can accept it. Otherwise
the mod leaves the cursor untouched for human recovery; normal vanilla menu
closure handles its own cursor. It never drops a stack as cancellation cleanup,
never completes the requested destination move after cancellation, and never
clicks a replacement menu. Already completed single-click swaps/drops are not
rolled back. Observers cannot start or cancel an animation.

### look — camera control

Three modes selected by the optional `mode` field (default
`"instant"`). The delta and smooth modes are advertised together as the
`camera` capability flag; instant mode predates the flag and is always
available. An unknown `mode` is a non-fatal `invalid_field` error.

```json
{"type": "look", "yaw": 90.0, "pitch": 0.0}
```

`mode: "instant"` — raw camera set, applied next tick with no
smoothing. Both fields required, finite numbers, degrees (Minecraft
convention: yaw 0 = south, increases clockwise; pitch −90 = up, +90 =
down). Cancels any active smoothed pan.

```json
{"type": "look", "mode": "delta", "yaw": 15.0, "pitch": -5.0}
```

`mode: "delta"` — relative offset in degrees, applied next tick. Both
fields required, finite. Deltas arriving between ticks accumulate; the
resulting pitch clamps to ±90. Cancels any active smoothed pan.

```json
{"type": "look", "mode": "smooth", "yaw": 90.0, "pitch": 10.0, "speed": 1.5}
{"type": "look", "mode": "smooth", "x": 100.5, "y": 64.0, "z": -20.5}
```

`mode: "smooth"` — the mod pans yaw/pitch toward the target over time,
frame-interpolated so rendered footage is smooth at any fps. The target
is **either** absolute `yaw`/`pitch` angles **or** a world point
`x`/`y`/`z` aimed at from the player's eye; supplying both, or neither,
is an `invalid_field` error. Yaw pans take the shortest way around; the
target pitch clamps to ±90. On convergence the exact target rotation is
written. Semantics:

- A point target re-aims from the current eye position every tick while
  the pan is active, so it stays accurate while the player moves. If a
  point becomes degenerate mid-pan (the eye reaches it), the previous
  tick's aim is kept.
- A point target equal to the player's eye position when the command is
  applied has no defined direction: an `invalid_field` error, sent at
  apply time (it echoes the offending frame but arrives after any
  observation frames already in flight). Per the usual error convention,
  the rejected message is not applied; any already-active pan continues
  unchanged.
- `speed` — optional positive finite multiplier on the mod's configured
  smoothing speed (`1.0` = config default, `2.0` = twice as fast).
  Non-positive or non-finite values are an `invalid_field` error.
- A new `look` in any mode replaces/cancels an active pan; `release`,
  agent disconnect, and leaving the world cancel it (the camera stays
  where it is — no snap-back).
- Success is silent: observation `yaw`/`pitch` report the actual,
  in-flight rotation, so agents detect convergence by watching them. A
  completion event is planned for the M4.6 event channel.

### release — everything to neutral

```json
{"type": "release"}
```

Release bypasses the ordinary command queue and cancels older queued commands
from the controller, including inventory work. Commands sent after release may
engage controls again.

### configure — per-session settings

```json
{"type": "configure", "rateDivisor": 5}
```

All fields are optional; **omitted fields are unchanged** (the same
convention as `input`). Success is silent. Settings apply to the current
session only and reset to the mod's configured defaults on disconnect.
Unlike `input`/`look`/`release`, `configure` is processed even while no
world is loaded.

- `rateDivisor` — integer 1–100: send one observation frame every N
  client ticks. Values outside the range, or non-integers, are a
  non-fatal `invalid_field` error. The default is the mod config's
  `observation.rateDivisor`.

- `sections` — optional array of section names, replacing this session's mask.
  Default `["player"]`; `[]` requests cadence-only frames. Duplicates are ignored.
  Currently only `"player"` is accepted; reserved future names `inventory`,
  `target`, `entities`, `world`, unknown names, non-arrays, and non-string entries
  fail with `invalid_field`. Invalid configure messages change no settings.
  Omitted masks stay unchanged; reconnect resets the default. Both roles may
  configure their own mask, including outside a world. Already queued/in-flight
  observations can still reflect previous settings.

## Mod → agent messages

### inventory_result — inventory request response

```json
{"type":"inventory_result","id":"read","op":"inspect","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3,"slots":[{"slot":9,"alias":"main.0","item":"minecraft:dirt","count":16}],"carried":{"item":"minecraft:air","count":0}}}
```

`slots` includes every slot (the example is abbreviated); empty stacks have
`item: "minecraft:air"`, `count: 0`. `alias` is omitted for non-player slots.
`carried` describes the cursor stack. Item ids and counts are deliberately
minimal; components and richer inventory observations arrive in M4.2.
Successful `close` returns `menu: null`. Other results report the menu after
local application. Results, like errors, never coalesce.

### observation — periodic state frame while in a world

```json
{"type":"observation","tick":1234,"player":{"x":12.5,"y":64.0,"z":-8.25,"yaw":90.0,"pitch":0.0,"velocity":{"x":0.0,"y":-0.0784,"z":0.0},"health":20.0,"maxHealth":20.0,"hunger":20,"saturation":5.0,"air":300,"maxAir":300,"xp":{"level":0,"progress":0.0,"total":0},"onGround":true,"inWater":false,"sneaking":false,"sprinting":false,"sleeping":false,"onFire":false,"effects":[]}}
```

`tick` counts client ticks since world join. Selected sections appear as named
objects at the root; unselected sections are omitted. Only `player` is currently
implemented. No placeholder sections are sent. With `sections: []`, frames
contain only `type` and `tick`.

Player fields are sampled together on the client thread at the end of the tick:

- `x/y/z`: feet position in blocks; `yaw/pitch`: actual rotation in degrees,
  including the latest rendered smoothing update, never the requested target.
- `velocity`: x/y/z in blocks per tick (client-side delta movement).
- `health/maxHealth`: health points, not hearts; `hunger`: food points (0–20).
  `saturation`: the client's known food saturation, which can lag server state.
- `air/maxAir`: air ticks; `air` can be negative while drowning.
- `xp`: integer `level`, fractional `progress` toward the next level, integer
  `total` experience as known by this client.
- Boolean flags: `onGround`, `inWater`, `sneaking` (crouching pose), `sprinting`,
  `sleeping`, `onFire`.
- `effects`: array sorted by namespaced effect `id`. Each entry contains `id`,
  integer `duration` in ticks (-1 means infinite), and zero-based integer
  `amplifier` (0 means level I). Empty when no effects are active.

These are client-visible values, not privileged server state. Observations are
sent only in a world, every `rateDivisor` client ticks, independently per
connection. At divisor 1, new client state appears in that tick's post-tick frame.

**Backpressure:** each connection coalesces observations to latest independently.
Tick gaps are expected for slow readers. Reliable replies never coalesce.

### error — malformed or invalid input

```json
{"type": "error", "code": "invalid_field", "message": "field \"pitch\" must be a number",
 "id": 12, "input": "{\"type\":\"look\",\"id\":12,\"yaw\":0,\"pitch\":\"up\"}"}
```

- `code` — machine-readable, from the taxonomy below.
- `message` — human-readable explanation; wording is not part of the
  contract and may change without a version bump.
- `id` — echoed if the offending message carried a valid `id`.
- `input` — the offending raw frame text, truncated to 256 characters. Present only when a frame caused the error.
- `supported` — only on `unsupported_version`: array of protocol versions
  the mod speaks.

| `code` | Fatal | Meaning |
|---|---|---|
| `invalid_json` | no* | Frame is not a JSON object |
| `unknown_type` | no* | Unrecognized `type` value |
| `invalid_field` | no* | Field missing, wrong type, or non-finite |
| `inventory_busy` | no | An animated inventory action is already running |
| `inventory_cancelled` | no | Animated action stopped before completion |
| `inventory_unavailable` | no | No usable world/menu or unsupported mode/menu |
| `stale_menu` | no | Menu identity or server state id changed |
| `inventory_impossible` | no | Slot/cursor/item rules prevent the operation |
| `unexpected_hello` | no | Repeated `hello` on an active session |
| `hello_required` | yes (1002) | First message was not `hello` |
| `unsupported_version` | yes (1002) | No shared protocol version |
| `unsupported_role` | yes (1002) | Role other than `controller` or `observer` |
| `controller_attached` | yes (1013) | A controller is already connected |
| `role_forbidden` | no | Observer sent a message its role may not send |
| `observer_attached` | yes (1013) | Observer limit reached |
| `overloaded` | yes (1013) | Command or reliable-output budget exhausted |

\* Fatal (close 1002) when it occurs during the handshake, i.e. before a
successful `hello`.

Non-fatal errors never close the connection and never alter held controls.

## Safety behavior (normative)

- On disconnect, socket error, or the client leaving the world, **all
  controls release within one client tick**. The player idles; nothing
  stays held.
- The release-all rule applies to sessions that completed `hello`. A
  connection that never completed the handshake is not a controller; its
  close is not an agent loss.
- Loss of an **observer** connection is not an agent loss: it releases
  nothing, affects no held control, and does not disturb the controller.
  Only controller loss triggers the release-all rule.
- Malformed input never crashes the client and never alters held controls.

### Emergency release

The local rebindable panic key (default F8) releases movement, jump, sneak,
sprint, attack/use holds and taps, pending hotbar changes, camera smoothing,
and inventory animation, and severs the controller. Observers remain attached.
Completed hotbar selections or inventory clicks are not rolled back; inventory
cancellation uses the safe cursor recovery rules above. Panic works in screens
and while paused. World exit also severs the controller to prevent stale work
from driving a subsequently joined world.

Controller loss/watchdog release runs at the next client tick or rendered frame,
whichever occurs first, before ordinary work. At 20 ticks/s with a responsive
client this is within 50 ms of loss detection; pong loss detection takes at most
configured timeout plus one watchdog interval (at most 1 second). No wall-clock
guarantee is possible while the Minecraft client thread itself is stalled.
