# Marionette protocol — version 2

> **Status: current (protocol 2; canonical path retained).** Supersedes [v0-draft.md](v0-draft.md). Versioning and
> change process are defined in [README.md](README.md).

## Migration from protocol 1

Only protocol 2 is accepted. Offer `versions: [2]`; move reads of `x`, `y`,
`z`, `yaw`, and `pitch` from the frame root to `frame.player`. `tick` stays
at the root. Commands and inventory results retain their existing shapes.

## Transport

- WebSocket, **text frames only**, one JSON object per frame.
- Endpoint: `ws://127.0.0.1:24680/` (loopback only; port and bind address
  configurable per M2.2). The address is resolved and validated once.
- HTTP requests carrying any Origin header, including `null`, receive HTTP
  403 before upgrade. Development clients must be native and omit Origin.
  Local processes are trusted without authentication; authentication remains
  a release gate (D16 in docs/decisions.md).
- A binary frame is a protocol violation: the connection closes with
  WebSocket close code `1003` (unsupported data), and any text frames
  already in flight behind it are discarded unprocessed.
- Messages over the frame-size limit (64 KiB) close the connection with
  close code `1009` (message too big).
- One **controller** connection at a time, plus up to `bridge.maxObservers`
  (default 2) read-only **observer** connections (see Handshake). Each
  connection has its own observation cadence and its own backpressure
  state: a slow reader only ever drops its own frames.
- A connection that has not completed the `hello` handshake within
  `bridge.helloTimeoutSeconds` (default 10) is closed with WebSocket close
  code `1002` and no error frame.
- **Liveness (`bridgeSafety`):** ping cadence is at most one second (or a
  quarter of the configured timeout). `bridge.pongTimeoutSeconds` defaults
  to 2 seconds (pings every 0.5 seconds), range 1–60, restart required. A
  session that supplies no pong by that deadline closes with 1008
  (`pong timeout`); other traffic does not renew the deadline. Timing starts
  when hello is admitted. Clients must keep answering pings: a client that
  stops reading for longer than the timeout minus one ping interval (1.5
  seconds at the default) can be disconnected.
- **Limits (`bridgeSafety`):** at most 128 queued commands per connection;
  one additional priority release slot. A full command queue closes only the
  offending connection with 1013 (`overloaded`) and a best-effort `overloaded`
  error. Each tick starts at most 32 commands and stops starting commands
  after 2 ms; a running vanilla action cannot be preempted. Connections are
  serviced round-robin. Release clears that controller's earlier queued work
  and precedes ordinary commands. Disconnect/panic invalidate queued work.
- Reliable text writes have a 256 KiB per-connection UTF-8 byte budget,
  including writes awaiting the network event loop; individual replies are
  limited to 128 KiB. Exceeding either limit disconnects with 1013. Replies
  never coalesce; on disconnect outstanding requests have unknown outcomes
  and must not be replayed blindly. A saturated channel may close without
  delivering its final error/close frame. Close flushing is limited to 250 ms.
- At most 8 connections may wait for HTTP upgrade/hello, with the hello
  timeout measured from TCP accept (including incomplete HTTP). Excess TCP
  connections are closed before upgrade. Established role limits are separate.
- Observations retain one latest stashed frame and at most one scheduled stash flush per
  connection, with a 128 KiB frame cap and the shared 256 KiB outbound budget.
  Observation overload coalesces; reliable overload disconnects. Events
  (`events`) have a separate per-connection bound and never coalesce; see
  Events below. Automatic
  pong replies also disconnect the offending peer on channel unwritability;
  control-frame floods cannot bypass output backpressure.
- **Shutdown:** when the game quits, the mod closes the connection with
  close code `1001` (going away) after releasing all controls.

## Envelope

Every message, in both directions, is a flat JSON object. Two top-level
keys are reserved:

- `type` — **required** string. Determines every other field's meaning.
  An unrecognized `type` from the agent is an `unknown_type` error.
- `id` — optional, a JSON string or number. Echoed verbatim in any reply
  the message causes (`error`, `hello`, `inventory_result`, or `scan_result`). Any other JSON
  type for `id` is an `invalid_field` error. The mod never generates ids
  of its own in v2; replies without a causing id omit the field. Unsolicited
  messages (`observation`, `event`) never carry `id` and never answer a request.

Unknown non-reserved fields are ignored (forward compatibility: additive
fields never break old agents). All other unknown input is an error.

## Handshake

The first message on a connection MUST be `hello`:

```json
{"type": "hello", "versions": [2], "role": "controller"}
```

- `versions` — required non-empty array of integers: every protocol
  version the agent speaks. The mod selects the highest version both
  sides support.
- `role` — optional string, default `"controller"`. Accepted values:
  `"controller"` (drives the player; at most one attached at a time) and
  `"observer"` (read-only observation stream — commentator agents,
  dashboards; capped by config). `"director"` (camera ownership split
  from movement) is a reserved name: it is rejected as
  `unsupported_role` until designed. An observer session may send only
  `hello` and `configure`; every other message is refused with a
  non-fatal `role_forbidden` error.

`sections` may also be supplied in hello, with the same validation and semantics
as configure below. It takes effect before the first observation. `events`
(boolean, default false) may likewise be supplied in hello to subscribe this
session to one-shot events before the first one can occur (see Events).

On success the mod replies, and the session is active:

```json
{"type": "hello", "version": 2, "capabilities": {"configure": true, "tap": true, "camera": true, "observer": true, "interact": true, "inventory": true, "inventoryAnimation": true, "playerState": true, "bridgeSafety": true, "panicLatch": true, "events": true, "inventoryState": true, "inventoryStorage": true, "targetState": true, "worldState": true, "entityState": true, "blockScan": true}, "mod": "0.1.0"}
```

- `version` — the selected protocol version.
- `capabilities` — feature flags. **Absent flag = unsupported**; agents
  feature-detect with a truthy check, never by version comparison.
  v2 flags: `configure` (the `configure` message below), `tap` (the
  `input.tap` one-shot field), `camera` (the `look` delta and smooth
  modes), `observer` (the mod accepts observer connections), `interact`
  (the `input` `attack`/`use` fields — held and tap — and `hotbar`).
  `inventory` advertises the controller-only inventory request/result API below.
  `inventoryAnimation` supports its opt-in `animated` field.
  `bridgeSafety` advertises the bounded transport and emergency behavior above.
  `panicLatch` advertises that local panic latches controller admission off
  until the human re-arms it (see Emergency release); observers can use it to
  feature-detect the latch. A controller never needs it to recognize a refusal.
  `playerState` advertises the player section and `sections` selection.
  `events` advertises the opt-in one-shot `event` stream (see Events).
  `inventoryState` advertises the `inventory` observation section, the item
  stack detail and the menu descriptor fields below (see Inventory section).
  `inventoryStorage` advertises generic storage support: mutation scope is
  decided by the storage analysis below rather than a fixed list of vanilla
  menus, menu descriptors carry `support`, and inventory errors carry a
  machine-readable `reason` (see Storage support and Rejection reasons).
  `targetState` advertises the `target` observation section (crosshair hit
  result, see Target section) and `worldState` the `world` section
  (dimension, time, weather and light, see World section).
  `entityState` advertises the `entities` observation section (nearby
  entities with hostility classification, see Entities section).
  `blockScan` advertises the controller-only `scan` request and its
  `scan_result` reply (bounded block scan, see scan below).
  Reserved names: `baritone`, `server`, `vision`, `blockChanges` and
  `blockScanBinary` (both see Block scan follow-ups).
- `mod` — informational mod version (semver, independent of the protocol
  version).

### Handshake rejection

Fatal rejections send an `error` message as the final text frame, then
close with the listed WebSocket close code:

| Condition | `code` | WS close |
|---|---|---|
| First message is not a valid `hello` (wrong type, malformed JSON, bad field) | `hello_required` / `invalid_json` / `invalid_field` / `unknown_type` | 1002 |
| No shared protocol version (error carries `supported`: array of versions the mod speaks) | `unsupported_version` | 1002 |
| `role` present but not `"controller"` or `"observer"` | `unsupported_role` | 1002 |
| A controller is already attached (in reply to a `controller` hello) | `controller_attached` | 1013 |
| The observer limit is reached (in reply to an `observer` hello) | `observer_attached` | 1013 |
| Local panic latch is engaged (in reply to a `controller` hello; see Emergency release) | `panic_latched` | 1008 |

During the handshake **every** error is fatal. A repeated `hello` on an
already-active session is the one exception by position: it arrives after
the handshake, and is a non-fatal `unexpected_hello` error (connection
stays open, held controls untouched).

## Agent → mod messages (after hello)

All commands accept an optional `id` (see Envelope). Except for `inventory` and `scan`, success is silent:
commands produce no reply; the next observation shows their effect.
While no world is loaded, `input`, `look`, and `release` are discarded.

### input — set-and-hold controls, one-shot taps, hotbar select

```json
{"type": "input", "forward": true, "sprint": true, "tap": ["jump"]}
{"type": "input", "hotbar": 0, "attack": true}
{"type": "input", "use": true}
{"type": "input", "tap": ["use"]}
```

Held fields (all optional booleans): `forward`, `back`, `left`,
`right`, `jump`, `sneak`, `sprint`, `attack`, `use`. **Omitted fields
are unchanged.** Held values persist until a later message changes them
(set-and-hold). `attack`/`use` and `hotbar` are advertised together as
the `interact` capability flag.

- Held `attack` behaves like a held left mouse button: it mines the
  targeted block continuously (and keeps mining while the window is
  unfocused). It does **not** repeat entity hits — vanilla swings only
  on clicks — so agents tap `attack` once per swing to fight; the
  vanilla attack cooldown applies either way.
- Held `use` behaves like a held right mouse button: eating, bow draw,
  block placement at vanilla's repeat rate.
- Starting to hold `attack` or `use` counts as one click (a vanilla
  press both holds the button and clicks it); re-sending `true` while
  already held clicks nothing.

`tap` — optional array of control names, each pressed for **exactly one
client tick** on the next tick, then auto-released; the agent never
times a press/release round-trip. v2 accepts `"jump"`, `"attack"`, and
`"use"`. Advertised as the `tap` capability flag. Semantics:

- Tapping a control that is already held is a no-op: the control stays
  held. A tap never releases anything.
- Duplicate entries in one array collapse; multiple `tap` messages
  arriving between ticks collapse to a single one-tick press.
- An `attack`/`use` tap the game could not consume on its tick (a
  screen was open) is dropped, never queued — a stale click must not
  fire when a menu closes later.
- A non-array `tap`, a non-string entry, or an unknown name is a
  non-fatal `invalid_field` error; the whole message is not applied.
- `release` — and every safety-triggered release-all — clears pending
  taps along with held controls.

`hotbar` — optional integer 0–8: select that hotbar slot on the next
tick. Out-of-range or non-integer values are a non-fatal
`invalid_field` error and the whole message is not applied. Slot
selection is world state, not a held control: `release` and the safety
release-all do **not** restore the previous slot. While a screen is
open the select is dropped (vanilla number keys mean hover-swap there,
not slot select).

**Screens:** opening any screen (inventory, chest, pause menu) releases
agent `attack`/`use` holds and drops pending `attack`/`use` taps and
`hotbar` selects — mirroring vanilla, which releases every key when a
screen opens. Holds do not resume when the screen closes; the agent
re-asserts them. Movement holds are unaffected (they deliberately
continue through GUIs).

### inventory — menu-addressed inventory actions

Advertised as `inventory`. Controller-only (including `inspect`); observers
remain read-only stream consumers. Each request gets one reliable
`inventory_result` or non-fatal `error`, echoing its optional `id`.
Unlike movement, requests without a live player fail with `inventory_unavailable`.

```json
{"type":"inventory","id":"open","op":"open"}
{"type":"inventory","id":"read","op":"inspect"}
{"type":"inventory","id":"move","op":"move","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3},"from":"main.0","to":"hotbar.0"}
{"type":"inventory","op":"swap","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3},"from":"main.1","hotbar":1}
{"type":"inventory","op":"equip","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3},"from":"main.2"}
{"type":"inventory","op":"drop","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3},"from":"hotbar.0","all":false}
{"type":"inventory","op":"close","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3}}
```

- `open` opens the survival inventory only when no screen is open and the
  player's inventory is the active menu. It never replaces another screen.
- `inspect` returns the current visible menu and its slots, or `menu: null`
  if no container screen is open. It is the same menu descriptor as the
  observation's `inventory.menu` (see Inventory section). With
  `inventoryState`, inspect also describes menus the mod cannot mutate (any
  container screen, and any game mode with a live player); their descriptor
  lists no `operations` and gives a `refusal`. Without a player it fails with
  `inventory_unavailable`.
- All other operations require `menu` with `type` (string), `containerId`
  and `stateId` (non-negative integers), copied from the latest result.
  They must match the active screen's actual menu at application time;
  mismatches fail with `stale_menu`. InventoryMenu has no registered type:
  `minecraft:inventory` is its protocol name. Other types use registry ids.
- Slot references (`from`, `to`) are either a non-negative menu slot index
  or a player alias: `hotbar.0`–`hotbar.8`, `main.0`–`main.26`,
  `armor.head`, `armor.chest`, `armor.legs`, `armor.feet`, `offhand`.
  Aliases resolve by backing player inventory and container slot, never by
  assuming where a menu puts player slots. An alias absent from that menu
  fails with `inventory_impossible`.
- `move` moves the entire source stack into an empty or matching destination.
  The entire stack must fit; incompatible/full destinations fail without
  clicking. Source and destination must differ.
- `swap` swaps the source stack with hotbar slot `hotbar` (integer 0–8).
  Both directions must satisfy slot pickup, placement and capacity rules.
- `equip` moves a single armor item into its matching, empty armor slot.
  That armor slot must exist in the current menu. Occupied armor is not replaced.
- `drop` drops one item, or the whole stack with `all: true` (default false).
- `close` uses vanilla container close, including its server notification.
  A nonempty cursor is refused rather than implicitly returning/dropping items.

All mutations run on the client tick through vanilla inventory clicks; they
never directly edit inventory stacks. Empty sources, occupied cursor, forbidden
slots, invalid destinations, and unsupported operations fail before any clicks
with `inventory_impossible`. For every operation except `inspect`, no open
menu, dead/spectator player, creative mode, or unrelated screen fails with
`inventory_unavailable`. Mutations are supported in the player's own inventory
menu and in menus that pass the storage analysis below (vanilla chest/barrel,
hopper, dispenser/dropper and shulker box menus pass it, as can modded
storage). Other menus fail with `inventory_unavailable`; they remain observable
and the wire addressing remains generic. Crafting input/result slots and bundle
click behavior are refused.

#### Storage support (`inventoryStorage`)

Mutation support is never granted by a menu's class or type name. A menu is a
**storage menu** when everything its slot clicks can do is vanilla behavior
whose outcome the mod predicts from the slots' own rules:

- the menu does not replace or extend vanilla click handling: of the vanilla
  menu methods, it may override only shift-click transfer, validity, closing,
  pick-all and drag eligibility, none of which the mod's clicks use;
- it synchronizes no menu data values (furnaces, brewing stands and other
  workstations do);
- each slot keeps vanilla stack handling and changes only its placement,
  pickup, capacity, activity or appearance rules; a slot backed by the player's
  inventory may also keep vanilla's equipment hook. Result slots and slots with
  take/insert side effects are excluded;
- no two slots address the same container position.

Each menu descriptor reports the outcome as `support` (see Inventory
section). In addition, every click is verified against the whole menu: after
each click, the involved slots and the cursor must hold exactly the predicted
stacks and every other slot must be unchanged. A deviation stops the sequence
with `inventory_impossible` (`reason` `unexpected_click`) and leaves any carried
stack visible, as for any unexpected vanilla behavior. Without
`inventoryStorage`, earlier mods supported exactly the vanilla menus listed
above.

Storage support covers the mechanical move, swap, equip, drop and close
operations only. It promises the slot rules the client can evaluate; a server
may still refuse or correct a click (for example after an update still in
flight), and the server's synchronized contents are authoritative. Server
corrections that arrive during an animated action cancel it
(`contents_changed`).

Results describe **client prediction**, not a server acknowledgment. Vanilla
server synchronization remains authoritative and may correct a predicted move.
The state id detects server updates, not every local edit; it is not an atomic
transaction or a permanent menu identifier. Re-inspect after synchronization
before dependent commands; do not pipeline operations based on an old snapshot.
By default all clicks for one action execute in the same tick. Unexpected vanilla click behavior stops the sequence
with `inventory_impossible`; any carried item remains visible for recovery,
never discarded by the mod.

#### Visible inventory interactions

`animated: true` on `move`, `equip`, `swap`, or `drop` enables the
`inventoryAnimation` capability. Default is false; non-boolean values are
`invalid_field`. Open/inspect/close accept the field but perform no animation.

```json
{"type":"inventory","id":"move","op":"move","animated":true,"menu":{"type":"minecraft:inventory","containerId":0,"stateId":3},"from":"main.0","to":"hotbar.0"}
```

The client draws an agent cursor over the actual inventory screen. It moves
smoothly to the source, pauses to click, and, for move/equip, carries the actual
vanilla cursor stack to the destination before placing it. Travel takes roughly
0.2–0.45 seconds per leg plus a short click pause. Swap uses the vanilla
number-key operation at the source; drop uses vanilla throw at the source.
These have one click cue rather than a carried-stack leg. The OS pointer is
not moved. Human mouse/keyboard input retains its own pointer and control.

Only one animated action may run at a time. Further mutations (including
open/close) fail with `inventory_busy`; inspect remains available. The result
arrives after the final click and is still a client prediction. No unbounded
animation queue exists. Await the result before sending a dependent command.

Each click revalidates the same player, screen, menu, slot contents and cursor.
`release`, controller loss, world exit, menu/screen replacement, or human
mouse press/scroll/key press cancels remaining clicks. Changed contents also
cancel the action. Cancellation reports `inventory_cancelled` if the requesting
connection remains available. A picked-up stack is returned through a vanilla
click only when the same live menu remains open, the carried stack is exactly
the one picked up, and the original source is empty and can accept it. Otherwise
the mod leaves the cursor untouched for human recovery; normal vanilla menu
closure handles its own cursor. It never drops a stack as cancellation cleanup,
never completes the requested destination move after cancellation, and never
clicks a replacement menu. Already completed single-click swaps/drops are not
rolled back. Observers cannot start or cancel an animation.

### scan — bounded block scan (`blockScan`)

Advertised as `blockScan`. An on-demand request for the blocks in a box near
the player; it is not a periodic stream and never appears in observations
(D3). Controller-only, like `inventory`: an observer's `scan` is refused with
`role_forbidden`. Each request gets exactly one reliable `scan_result` or
non-fatal `error`, echoing its optional `id`. Agents that never send `scan`
never receive either.

```json
{"type":"scan","id":"terrain","size":{"x":16,"y":8,"z":16}}
{"type":"scan","id":"pit","min":{"x":-8,"y":-62,"z":-8},"size":{"x":16,"y":8,"z":16}}
```

- `size` — required object with integer `x`, `y`, `z`, each 1–8192: the box
  extent in blocks along each axis.
- `min` — optional object with integer `x`, `y`, `z`: the box's lowest corner,
  in absolute block coordinates (inclusive). The box covers `min` to
  `min + size − 1` on each axis. Without `min` the box is centred on the
  player's feet block (as `world.feet`) when the request is applied:
  `min = feet − floor(size / 2)` on each axis. The result always reports the
  `min` actually used.
- A missing or non-object `size`, a non-object `min`, or a missing,
  non-integer or out-of-range component is a non-fatal `invalid_field` error.

**Caps (normative).** Checked when the request is applied, against the player's
feet block at that moment; a refused request scans nothing:

- **Radius:** every position in the box must lie within
  `observation.blockScanRadius` blocks of the feet block along each axis
  (`|x − feet.x|`, `|y − feet.y|` and `|z − feet.z|` each at most the radius).
  The config range is 4–32, default 16, applied live. Otherwise the request
  fails with `scan_refused`, reason `over_radius`.
- **Volume:** `size.x × size.y × size.z` must be at most 8192 blocks (a fixed
  protocol limit that keeps every result well inside the 128 KiB reply limit).
  Otherwise it fails with `scan_refused`, reason `over_volume`.

Both refusals carry `limits`: `{"radius": <current radius>, "maxVolume": 8192}`,
so an agent can shrink the request without guessing. A refusal is non-fatal: the
session, held controls and any other work are unaffected.

```json
{"type":"error","code":"scan_refused","reason":"over_radius","message":"scan box exceeds the configured radius 16 around the player","id":"far","limits":{"radius":16,"maxVolume":8192},"input":"{\"type\":\"scan\",\"id\":\"far\",\"min\":{\"x\":100,\"y\":-60,\"z\":0},\"size\":{\"x\":16,\"y\":8,\"z\":16}}"}
```

**Work budget (normative).** A scan is read on the client thread at the end of
client ticks, in index order (below), at most
`observation.blockScanBlocksPerTick` positions per tick (config 64–8192,
default 1024, applied live). The first portion is read at the end of the tick
in which the request is applied, so a scan of V blocks completes on its
`ceil(V / budget)`-th tick: a 16×8×16 scan (2048 blocks) at the default budget
spans two ticks. Reading a portion never blocks the render thread for more than
that portion. The result is sent at the end of the completing tick, before that
tick's observation.

- **One scan at a time.** A `scan` applied while another is in progress fails
  with `scan_refused`, reason `busy`; await the result before sending the next.
- **Not a snapshot.** Each position reflects the client's world on the tick it
  was read; blocks that change during a multi-tick scan may appear in either
  state. `startTick` and `tick` bound the read.
- **Cancellation.** `release` (and every safety release: controller loss, panic)
  cancels an in-progress scan with `scan_cancelled`, reason `released`, as for
  inventory work. Leaving the world cancels it with reason `world_exit`, and a
  dimension change or replaced client level with `level_changed`. Commands
  still queued behind a `release` are discarded unanswered, as for every
  command. A cancelled scan sends no partial result. No reply reaches a
  disconnected agent.
- Without a live player the request fails with `scan_refused`, reason
  `no_world`.

### look — camera control

Three modes selected by the optional `mode` field (default
`"instant"`). The delta and smooth modes are advertised together as the
`camera` capability flag; instant mode predates the flag and is always
available. An unknown `mode` is a non-fatal `invalid_field` error.

```json
{"type": "look", "yaw": 90.0, "pitch": 0.0}
```

`mode: "instant"` — raw camera set, applied next tick with no
smoothing. Both fields required, finite numbers, degrees (Minecraft
convention: yaw 0 = south, increases clockwise; pitch −90 = up, +90 =
down). Cancels any active smoothed pan.

```json
{"type": "look", "mode": "delta", "yaw": 15.0, "pitch": -5.0}
```

`mode: "delta"` — relative offset in degrees, applied next tick. Both
fields required, finite. Deltas arriving between ticks accumulate; the
resulting pitch clamps to ±90. Cancels any active smoothed pan.

```json
{"type": "look", "mode": "smooth", "yaw": 90.0, "pitch": 10.0, "speed": 1.5}
{"type": "look", "mode": "smooth", "x": 100.5, "y": 64.0, "z": -20.5}
```

`mode: "smooth"` — the mod pans yaw/pitch toward the target over time,
frame-interpolated so rendered footage is smooth at any fps. The target
is **either** absolute `yaw`/`pitch` angles **or** a world point
`x`/`y`/`z` aimed at from the player's eye; supplying both, or neither,
is an `invalid_field` error. Yaw pans take the shortest way around; the
target pitch clamps to ±90. On convergence the exact target rotation is
written. Semantics:

- A point target re-aims from the current eye position every tick while
  the pan is active, so it stays accurate while the player moves. If a
  point becomes degenerate mid-pan (the eye reaches it), the previous
  tick's aim is kept.
- A point target equal to the player's eye position when the command is
  applied has no defined direction: an `invalid_field` error, sent at
  apply time (it echoes the offending frame but arrives after any
  observation frames already in flight). Per the usual error convention,
  the rejected message is not applied; any already-active pan continues
  unchanged.
- `speed` — optional positive finite multiplier on the mod's configured
  smoothing speed (`1.0` = config default, `2.0` = twice as fast).
  Non-positive or non-finite values are an `invalid_field` error.
- A new `look` in any mode replaces/cancels an active pan; `release`,
  agent disconnect, and leaving the world cancel it (the camera stays
  where it is — no snap-back).
- Success is silent: observation `yaw`/`pitch` report the actual,
  in-flight rotation, so agents detect convergence by watching them. No pan
  completion event exists yet; it may be added later as an event kind.

### release — everything to neutral

```json
{"type": "release"}
```

Release bypasses the ordinary command queue and cancels older queued commands
from the controller, including inventory work. Commands sent after release may
engage controls again.

### configure — per-session settings

```json
{"type": "configure", "rateDivisor": 5}
```

All fields are optional; **omitted fields are unchanged** (the same
convention as `input`). Success is silent. Settings apply to the current
session only and reset to the mod's configured defaults on disconnect.
Unlike `input`/`look`/`release`, `configure` is processed even while no
world is loaded.

- `rateDivisor` — integer 1–100: send one observation frame every N
  client ticks. Values outside the range, or non-integers, are a
  non-fatal `invalid_field` error. The default is the mod config's
  `observation.rateDivisor`.

- `sections` — optional array of section names, replacing this session's mask.
  Default `["player"]`; `[]` requests cadence-only frames. Duplicates are ignored.
  Accepted names are `"player"` (`playerState`), `"inventory"`
  (`inventoryState`), `"target"` (`targetState`), `"world"` (`worldState`)
  and `"entities"` (`entityState`). Unknown names, non-arrays, and
  non-string entries fail with `invalid_field`.
  Invalid configure messages change no settings.
  Omitted masks stay unchanged; reconnect resets the default. Both roles may
  configure their own mask, including outside a world. Already queued/in-flight
  observations can still reflect previous settings.

- `events` — optional boolean (`events` capability): subscribe (`true`) or
  unsubscribe (`false`) this session from one-shot events. Default false;
  reconnect resets it. Non-booleans fail with `invalid_field`. Like other
  configure fields it is applied on the client tick; events recorded before
  it applies are not delivered and are never replayed. Both roles may subscribe.

## Mod → agent messages

### inventory_result — inventory request response

```json
{"type":"inventory_result","id":"read","op":"inspect","menu":{"type":"minecraft:inventory","containerId":0,"stateId":3,"slots":[{"slot":9,"alias":"main.0","item":"minecraft:dirt","count":16}],"carried":{"item":"minecraft:air","count":0}}}
```

`slots` includes every slot (the example is abbreviated); empty stacks have
`item: "minecraft:air"`, `count: 0`. `alias` is omitted for non-player slots.
`carried` describes the cursor stack. With `inventoryState`, `menu` is the full
menu descriptor and every stack carries the bounded item detail described under
Inventory section below; the fields above keep their meaning.
Successful `close` returns `menu: null`. Other results report the menu after
local application. Results, like errors, never coalesce.

### scan_result — block scan response (`blockScan`)

Sent only in reply to a `scan` (see scan above), echoing its `id`. Never
coalesced; like every reply it counts toward the reliable output budget.

```json
{"type":"scan_result","id":"pit","dimension":"minecraft:overworld","min":{"x":10,"y":64,"z":-3},"size":{"x":3,"y":2,"z":2},"order":"yzx","startTick":812,"tick":812,"palette":["minecraft:stone","minecraft:dirt","minecraft:water","minecraft:air","minecraft:oak_log"],"indices":[0,0,1,0,2,1,3,3,4,3,3,3]}
```

| Field | Meaning |
|---|---|
| `dimension` | Dimension (level) registry id the blocks were read from |
| `min`, `size` | The box actually scanned (absolute lowest corner, extent per axis) |
| `order` | Always `"yzx"`: the index order below. Present so a result is self-describing |
| `startTick`, `tick` | The observation ticks (see observation) on which the first and the last positions were read |
| `palette` | The distinct block registry ids in the box, each once, in order of first appearance in `indices`. A `null` entry means "no block data": the position is in a chunk the client has not loaded |
| `indices` | `size.x × size.y × size.z` integers, one per position, each an index into `palette` |

**Encoding (normative).** Positions are listed **y-major, then z, then x**
(x varies fastest). For a position `(x, y, z)` inside the box, with
`dx = x − min.x`, `dy = y − min.y`, `dz = z − min.z`:

```text
i = (dy × size.z + dz) × size.x + dx
block(x, y, z) = palette[indices[i]]
```

Conversely entry `i` is at `dx = i mod size.x`,
`dz = floor(i / size.x) mod size.z`, `dy = floor(i / (size.x × size.z))`.

*Worked example* (the result above, a 3×2×2 box at `min` (10, 64, −3)):

| `i` | `dy` | `dz` | `dx` | Position | `indices[i]` | Block |
|---|---|---|---|---|---|---|
| 0–2 | 0 | 0 | 0–2 | (10–12, 64, −3) | 0, 0, 1 | stone, stone, dirt |
| 3–5 | 0 | 1 | 0–2 | (10–12, 64, −2) | 0, 2, 1 | stone, water, dirt |
| 6–8 | 1 | 0 | 0–2 | (10–12, 65, −3) | 3, 3, 4 | air, air, oak_log |
| 9–11 | 1 | 1 | 0–2 | (10–12, 65, −2) | 3, 3, 3 | air, air, air |

The water at (11, 64, −2) is `i = (0 × 2 + 1) × 3 + 1 = 4`, `indices[4] = 2`,
`palette[2] = "minecraft:water"`. The palette lists stone first because index 0
is stone.

- Entries are block ids, not block states: properties such as facing, stair
  shape, fluid level or `waterlogged` are not reported. Fluids appear as their
  blocks (`minecraft:water`, `minecraft:lava`); a waterlogged block appears as
  the block itself. Air variants are reported as they are (`minecraft:air`,
  `minecraft:cave_air`); positions outside the dimension's build height read as
  `minecraft:void_air`, as vanilla reports them.
- Values are what the client knows: what the server sent for loaded chunks,
  plus local predictions (a block the player just broke reads as broken before
  the server confirms it).
- Agents must not assume a palette order beyond the definition above, a
  palette size, or that every palette entry differs from a known id set;
  modded block ids appear like vanilla ones.

If the encoded result would exceed the 128 KiB reply limit (only possible with
very long modded ids), the mod sends `scan_cancelled`, reason `too_large`,
instead, so the session is never closed for an oversized scan.

#### Block scan follow-ups (reserved, not implemented)

- **Block changes:** the event kind `block_changed` and the capability
  `blockChanges` are reserved for a post-v1 follow-up that reports changes to
  blocks inside a scanned box, so an agent can keep a scan current without
  rescanning. This mod never sends them; agents must not expect them unless a
  future hello advertises `blockChanges`.
- **Binary frames:** the capability `blockScanBinary` is reserved for carrying
  the same structure in a binary WebSocket frame (the header fields above as
  JSON, `palette` and `indices` as packed data) if profiling ever demands it.
  The palette and index order would not change. Until a future hello
  advertises that capability and the agent opts in, binary frames remain a
  protocol violation in both directions.

### observation — periodic state frame while in a world

```json
{"type":"observation","tick":1234,"player":{"x":12.5,"y":64.0,"z":-8.25,"yaw":90.0,"pitch":0.0,"velocity":{"x":0.0,"y":-0.0784,"z":0.0},"health":20.0,"maxHealth":20.0,"hunger":20,"saturation":5.0,"air":300,"maxAir":300,"xp":{"level":0,"progress":0.0,"total":0},"onGround":true,"inWater":false,"sneaking":false,"sprinting":false,"sleeping":false,"onFire":false,"effects":[]}}
```

`tick` counts client ticks since world join. Selected sections appear as named
objects at the root, in the order `player`, `inventory`, `target`, `world`,
`entities`; unselected sections are omitted. All five are implemented. No placeholder sections are sent. With `sections: []`, frames
contain only `type` and `tick`.

Player fields are sampled together on the client thread at the end of the tick:

- `x/y/z`: feet position in blocks; `yaw/pitch`: actual rotation in degrees,
  including the latest rendered smoothing update, never the requested target.
- `velocity`: x/y/z in blocks per tick (client-side delta movement).
- `health/maxHealth`: health points, not hearts; `hunger`: food points (0–20).
  `saturation`: the client's known food saturation, which can lag server state.
- `air/maxAir`: air ticks; `air` can be negative while drowning.
- `xp`: integer `level`, fractional `progress` toward the next level, integer
  `total` experience as known by this client.
- Boolean flags: `onGround`, `inWater`, `sneaking` (crouching pose), `sprinting`,
  `sleeping`, `onFire`.
- `effects`: array sorted by namespaced effect `id`. Each entry contains `id`,
  integer `duration` in ticks (-1 means infinite), and zero-based integer
  `amplifier` (0 means level I). Empty when no effects are active.

These are client-visible values, not privileged server state. Observations are
sent only in a world, every `rateDivisor` client ticks, independently per
connection. At divisor 1, new client state appears in that tick's post-tick frame.

#### Inventory section (`inventoryState`)

Selected with `sections` containing `"inventory"`; never sent otherwise, so
clients that do not select it see unchanged frames. Sampled on the client thread
at the end of the tick together with `player`.

```json
{"type":"observation","tick":1300,"inventory":{"selected":0,"mainHand":{"item":"minecraft:diamond_sword","count":1,"damage":12,"maxDamage":1561,"name":"Edge","enchantments":[{"id":"minecraft:sharpness","level":3}]},"hotbar":[{"item":"minecraft:diamond_sword","count":1,"damage":12,"maxDamage":1561,"name":"Edge","enchantments":[{"id":"minecraft:sharpness","level":3}]},{"item":"minecraft:bread","count":5}],"main":[{"item":"minecraft:air","count":0}],"armor":{"head":{"item":"minecraft:air","count":0},"chest":{"item":"minecraft:iron_chestplate","count":1,"damage":0,"maxDamage":240},"legs":{"item":"minecraft:air","count":0},"feet":{"item":"minecraft:air","count":0}},"offhand":{"item":"minecraft:shield","count":1,"damage":0,"maxDamage":336},"menu":null}}
```

(`hotbar` always has 9 entries and `main` 27; the example is abbreviated.)

- `selected` — selected hotbar index 0–8. `mainHand` — the held stack, equal to
  `hotbar[selected]`.
- `hotbar[i]` is the stack addressed by alias `hotbar.i`; `main[i]` by `main.i`;
  `armor.head|chest|legs|feet` by `armor.head` ...; `offhand` by `offhand`.
- `menu` — the visible container menu descriptor, exactly as `inspect` would
  return it at that moment, or `null` when no container screen is open. The
  survival inventory screen is `minecraft:inventory`. The creative inventory
  screen is not a player-addressable menu and reports `null`.

**Item stack.** Every stack (section entries, menu slots, `carried`, and
`inventory_result` stacks) has `item` (registry id; `minecraft:air` when empty)
and `count`. Non-empty stacks add only the following enumerated extras, each
omitted when absent:

| Field | Meaning |
|---|---|
| `damage`, `maxDamage` | Durability for damageable items, both integers (present even at damage 0); remaining uses = `maxDamage - damage` |
| `name` | Custom (renamed) display name as plain text, at most 64 UTF-16 characters; longer names are cut and add `nameTruncated: true` |
| `enchantments` | Array of `{"id", "level"}` sorted by id, at most 8 entries; more add `enchantmentsTruncated: true` |
| `storedEnchantments` | The same for enchanted books' stored enchantments (`storedEnchantmentsTruncated`) |
| `potion` | Base potion id of potions, splash/lingering potions and tipped arrows |

No other component is serialized (lore, custom data, container contents,
attributes, custom effects, trims and similar are deliberately absent).
Agents must ignore stack fields they do not know.

**Menu descriptor.** `inspect` results and `inventory.menu` share one shape:

| Field | Meaning |
|---|---|
| `type`, `containerId`, `stateId` | Menu reference for actions (D8), as before |
| `slotCount` | Number of slots in the menu |
| `slots` | `{"slot", "alias"?, "refused"?, ...stack}` in slot-index order |
| `carried` | Cursor stack |
| `operations` | Mutating ops the mod would currently attempt on this menu, from `move`, `swap`, `equip`, `drop`, `close`; per-slot rules still apply |
| `refusal` | `null` when `operations` is non-empty, otherwise why none apply (below) |
| `support` | With `inventoryStorage`: `{"scope", "reasons"}`, the menu's mutation support independent of the player, cursor and busy state (below) |

`refusal` values, in precedence order: `player_unavailable` (dead, spectator
or creative player), `unsupported_menu` (menu implementation outside the
mutation scope; observable only), `busy` (an animated action is running),
`cursor_occupied` (a carried stack blocks every mutation, including close).
`equip` appears only when the menu contains the player's armor slots.
In a menu within the mutation scope (`refusal` is `null`, `busy` or
`cursor_occupied`), a slot the mod will never act on carries `refused`:
`crafting` (non-player slots of the survival inventory), `inactive`, or
`bundle` (the slot holds a bundle). Requests against refused slots fail with
`inventory_impossible`; against a refused menu with the corresponding error
(`inventory_unavailable`, `inventory_busy`, or `inventory_impossible`).
Further `refusal` and `refused` values may be added under the same capability;
agents treat an unknown value as a refusal.

`support.scope` is `"player"` for the player's own inventory menu,
`"storage"` for a menu that passed the storage analysis, or `null`, in which
case the menu is never mutated (`refusal` is `unsupported_menu` unless
`player_unavailable` takes precedence). `support.reasons` is empty unless
`scope` is `null`, and then lists every failed rule, sorted:

| `reasons` value | Meaning |
|---|---|
| `click_behavior` | The menu replaces or extends vanilla click handling or other menu behavior the analysis does not cover |
| `menu_data` | The menu synchronizes data values (furnace, brewing stand, enchanting table and other workstations) |
| `slot_behavior` | A slot changes behavior beyond placement, pickup, capacity, activity and appearance rules (result slots, take/insert side effects) |
| `shared_slots` | Two slots address the same container position |

```json
{"type":"minecraft:furnace","containerId":4,"stateId":1,"slotCount":39,"slots":[],"carried":{"item":"minecraft:air","count":0},"operations":[],"refusal":"unsupported_menu","support":{"scope":null,"reasons":["menu_data","slot_behavior"]}}
```

(`slots` abbreviated.) Further `reasons` values may be added; agents treat any `null` scope as
unsupported regardless of the reasons they recognize.

**Size bound.** An `inventory` section, and an `inspect` result's `menu`, is
limited to 96 KiB of UTF-8 JSON. If the full form exceeds it, every stack is
reduced to `item`, `count`, `damage` and `maxDamage`, and the bounded object
(the `inventory` section, or the `inspect` result's `menu`) carries
`reduced: true`. If it is still too large, trailing menu slots are omitted and
the menu carries `truncated: true` (`slotCount` keeps the real number). Both
flags are absent otherwise.

#### Target section (`targetState`)

Selected with `sections` containing `"target"`; never sent otherwise. It reports
vanilla's own crosshair hit result: the block or entity the crosshair outline
highlights and that `attack` and `use` act on.

```json
{"type":"observation","tick":1400,"target":{"kind":"block","pos":{"x":3,"y":-60,"z":1},"block":"minecraft:oak_log","face":"north","hit":{"x":3.62,"y":-59.31,"z":1.0},"distance":2.734,"reach":{"block":4.5,"entity":3.0}}}
{"type":"observation","tick":1460,"target":{"kind":"entity","id":187,"entity":"minecraft:pig","hit":{"x":0.21,"y":-59.48,"z":-2.55},"distance":2.118,"reach":{"block":4.5,"entity":3.0}}}
{"type":"observation","tick":1520,"target":{"kind":"none","reach":{"block":4.5,"entity":3.0}}}
```

- `kind` — `"block"`, `"entity"` or `"none"`. Agents treat an unknown kind
  like `"none"`. Every kind carries `reach`; the other fields follow the kind.
- Block: `pos` (integer block position), `block` (block registry id) and `face`
  (the hit face: `down`, `up`, `north`, `south`, `west` or `east`).
- Entity: `id` (the client's integer entity id, stable while the entity stays
  loaded in this world session and never reused as a durable identity) and
  `entity` (entity type registry id).
- Block and entity: `hit`, the exact hit point in world coordinates, and
  `distance`, the distance in blocks from the camera entity's eye to `hit`.
- `reach` — `block` and `entity`, the player's current interaction ranges in
  blocks (attributes `minecraft:block_interaction_range` and
  `minecraft:entity_interaction_range`; vanilla survival 4.5 and 3.0, creative
  5.0 and 5.0). Modifiers from effects, items or mods apply.

**Reach semantics (normative).** The target is exactly vanilla's crosshair pick
(`Minecraft.hitResult`); the mod casts no ray of its own and offers no extended
"gaze" distance:

- The ray starts at the camera entity's eye (the player unless spectating
  another entity) along its view direction. Blocks are tested against their
  interaction outline; fluids are never targets and the ray passes through
  them. Entities must be pickable (not spectators, item entities or other
  non-interactive entities); the nearer of block and entity wins.
- A block counts only within `reach.block`, an entity only within
  `reach.entity`. Anything farther is `"none"`, even if visible, and so is
  open sky. An entity farther than `reach.entity` but in front of a block
  within `reach.block` hides that block (vanilla behavior): the result is
  `"none"`, as the crosshair shows.
- Vanilla recomputes the pick every rendered frame from the latest rendered
  rotation (including smoothing, see `look`). The section reports the value as
  of the end of the tick, so it agrees with `player.yaw/pitch` in the same
  frame. Before the first frame in a world the target is `"none"`.
- The F3 debug screen's "Targeted Block" uses a separate fixed 20-block ray.
  It agrees with `target` within `reach.block` when no entity is in front;
  beyond reach F3 can still name a block while `target` is `"none"`. Its
  "Targeted Entity" is the same entity as `target`.

Seeing farther than reach is deliberately left to the `entities` section (see
Entities section) and block scans (see scan). A longer gaze ray, if needed, would be a separate
opt-in addition and would not change `target`.

#### World section (`worldState`)

Selected with `sections` containing `"world"`; never sent otherwise. Client-known
values sampled at the end of the tick.

```json
{"type":"observation","tick":1600,"world":{"dimension":"minecraft:overworld","dayTime":30000,"timeOfDay":6000,"day":1,"weather":"rain","rainLevel":1.0,"thunderLevel":0.0,"feet":{"x":0,"y":-60,"z":0},"light":{"block":0,"sky":15,"combined":15,"effective":12}}}
```

- `dimension` — dimension (level) registry id.
- `dayTime` — the level's day time in ticks as known by the client (it can
  exceed 24000 and does not advance while `doDaylightCycle` is false).
  `timeOfDay` is `dayTime` modulo 24000 (0 sunrise, 6000 noon, 13000 night,
  18000 midnight); `day` is `dayTime` divided by 24000, rounded down (F3's
  "Day"). Dimensions with fixed time report the stored value unchanged.
- `weather` — `"clear"`, `"rain"` or `"thunder"`, the level-wide state using
  vanilla's thresholds (rain above 0.2, thunder above 0.9). Snow in cold biomes
  is `"rain"`. Dimensions without weather are always `"clear"`.
  `rainLevel` and `thunderLevel` (0.0–1.0) are the client's current intensities;
  they fade in and out over several seconds, so `weather` changes after the
  command that caused it. `thunderLevel` already includes the rain factor.
- `feet` — the integer block position containing the player's feet (F3's
  "Block:"), where light is sampled.
- `light` — `block` and `sky` light levels (0–15) at `feet`; `combined`, their
  maximum (F3's "Client Light"); `effective`, the same with the sky part reduced
  for time of day and weather (the vanilla local brightness).

#### Entities section (`entityState`)

Selected with `sections` containing `"entities"`; never sent otherwise. The
entities the client knows within a configured radius of the player, nearest
first, sampled on the client thread at the end of the tick.

```json
{"type":"observation","tick":1700,"entities":{"radius":32,"maxCount":64,"total":3,"truncated":false,"nearby":[{"id":212,"type":"minecraft:zombie","hostility":"hostile","x":3.5,"y":-60.0,"z":1.5,"velocity":{"x":-0.021,"y":0.0,"z":0.034},"distance":3.808,"health":20.0,"maxHealth":20.0,"targetingMe":"unknown"},{"id":215,"type":"minecraft:item","hostility":"item","x":-1.2,"y":-60.0,"z":5.1,"velocity":{"x":0.0,"y":0.0,"z":0.0},"distance":5.239,"item":{"item":"minecraft:diamond","count":3}},{"id":213,"type":"minecraft:cow","hostility":"passive","x":-6.5,"y":-60.0,"z":-3.5,"velocity":{"x":0.0,"y":0.0,"z":0.0},"distance":7.382,"health":10.0,"maxHealth":10.0,"targetingMe":"unknown"}]}}
```

- `radius` — the radius in blocks that was searched, and `maxCount` the most
  entries listed, both from the mod configuration (`observation.entityRadius`,
  4–64, default 32, and `observation.entityMaxCount`, 1–256, default 64). They
  apply to every session alike and take effect live when the config changes.
- `total` — how many entities were within `radius`; `truncated` — `true` when
  `total` exceeded `maxCount`, so only the nearest `maxCount` are listed.
  `truncated` is always present.
- `nearby` — the entries, sorted by `distance` ascending (ties by `id`).

An entity is in range when the straight-line distance from the player's feet
position (`player.x/y/z`) to the entity's position is at most `radius`. The
local player itself is never listed; every other entity loaded on the client
is a candidate, including other players, spectators, invisible mobs, item
entities, projectiles, vehicles and decorations. Parts of multipart entities
(the ender dragon's hitboxes) are not separate entries.

Every entry has:

| Field | Meaning |
|---|---|
| `id` | The client's integer entity id, as in `target` (stable while the entity stays loaded; never a durable identity) |
| `type` | Entity type registry id |
| `hostility` | `"hostile"`, `"neutral"`, `"passive"`, `"player"`, `"item"` or `"other"` (below). Agents treat an unknown value like `"other"` |
| `x/y/z` | Position in blocks, as the client currently shows it (feet for mobs and players) |
| `velocity` | x/y/z in blocks per tick: the entity's change of client position over the last tick (what the client rendered, including the interpolation of server updates) |
| `distance` | Distance in blocks from the player's feet position to `x/y/z` |

Living entities (mobs, players, armor stands) add `health` and `maxHealth`
(health points, as synchronized to the client) and `targetingMe` (below).
Players add `name` (the profile name). Item entities add `item`, the dropped
stack's `item` id and `count`. Other fields are absent; agents must ignore
fields they do not know.

**Hostility (normative).** A fixed classification of the entity's *type*, not
its current mood: an angered wolf stays `"neutral"` and a tamed one is still a
wolf. Precedence:

1. `"player"` — any player entity.
2. `"item"` — a dropped item entity (`minecraft:item`). Experience orbs and
   other pickups are `"other"`.
3. The vanilla table below, for the types it names.
4. Otherwise by the entity's class: a neutral mob (vanilla `NeutralMob`) is
   `"neutral"`; an enemy (vanilla `Enemy`, or a mob whose spawn category is
   `monster`) is `"hostile"`; any other mob is `"passive"`; everything else
   (vehicles, projectiles, armor stands, decorations, displays, experience
   orbs, modded non-mobs) is `"other"`.

| `hostility` | Vanilla types |
|---|---|
| `hostile` | blaze, bogged, breeze, creaking, creeper, drowned, elder_guardian, ender_dragon, endermite, evoker, ghast, giant, guardian, hoglin, husk, illusioner, magma_cube, phantom, piglin_brute, pillager, ravager, shulker, silverfish, skeleton, slime, stray, vex, vindicator, warden, witch, wither, wither_skeleton, zoglin, zombie, zombie_villager |
| `neutral` | bee, cave_spider, dolphin, enderman, goat, iron_golem, llama, panda, piglin, polar_bear, spider, trader_llama, wolf, zombified_piglin |
| `passive` | every other vanilla mob: allay, armadillo, axolotl, bat, camel, cat, chicken, cod, cow, donkey, fox, frog, glow_squid, happy_ghast, horse, mooshroom, mule, ocelot, parrot, pig, pufferfish, rabbit, salmon, sheep, skeleton_horse, sniffer, snow_golem, squid, strider, tadpole, tropical_fish, turtle, villager, wandering_trader, zombie_horse |

`"neutral"` means the type attacks only when provoked or under conditions
(spiders in darkness, endermen looked at, piglins without gold armor, goats
ramming); `"hostile"` attacks players on sight. Neither says what the entity is
doing now; see `targetingMe`.

**`targetingMe` (normative).** Whether this living entity is currently
attacking the local player, reported only when the client actually knows:

- `"yes"` / `"no"` — the entity synchronizes its attack target to clients and
  that target is the local player / another entity. In vanilla only guardians
  and elder guardians (the target of the beam, from the moment it starts) and
  the wither (its main target) do.
- `"unknown"` — everything else, including every entity without a synchronized
  target, and those entities while their synchronized target is empty. Most
  mobs, zombies included, never tell the client what they target.

The value follows the synchronized data, which reaches the client a few ticks
after the server changes it, like positions and health. The mod does not infer
intent from distance, facing, raised arms, anger timers or damage taken; such
heuristics are left to agents. Further values may
be added; agents treat an unknown value like `"unknown"`.

These are client-visible values, not privileged server state. The server only
sends the client entities within its entity tracking range (which depends on
the entity type and the server's view distance), so entities beyond it are
never listed whatever the radius. Positions of other entities reach the client
periodically and are interpolated; they can lag the server by a few ticks.

**Backpressure:** each connection coalesces observations to latest independently.
Tick gaps are expected for slow readers. Reliable replies never coalesce. Events never
coalesce; they have their own bound (see Events).

### event — one-shot things that happened (`events`)

Observations describe state that *is*; events report things that *happened*.
Events are **opt-in**: a session receives them only after subscribing with
`events: true` in `hello` or `configure`, and only when the hello reply
advertises the `events` capability. Agents that predate events never subscribe
and therefore never receive the `event` type; marionette-mc 0.1.0a1, for
example, treats an unknown message type as a fatal decoding failure.

```json
{"type":"event","event":"damage","seq":7,"worldSession":"5d0c6f3e9a4b2c18","tick":812,"basis":"server","source":{"type":"minecraft:generic","attacker":null,"direct":null},"amount":3.0,"health":17.0}
```

Envelope fields, present on every event:

- `event` — the kind (taxonomy below). Further kinds may be added under the
  same capability; agents must ignore kinds they do not know, while still
  counting their `seq`.
- `seq` — integer, per connection. The first event delivered on a connection is
  1 and each later one is exactly one more. A connection never skips a number:
  if an event cannot be delivered, the connection is closed instead (see
  Overflow). Numbering restarts at 1 on every connection.
- `worldSession` — opaque string, newly generated each time the client joins a
  world (singleplayer or server). It stays the same across death, respawn and
  dimension changes. Compare it only for equality.
- `tick` — the client tick within that world session during which the event was
  recorded. It is the `tick` of the observation sampled at the end of that tick.
- `basis` — how the client knows: `"server"` means a server packet reported it
  to this client; `"client"` means the client **predicted** it locally and the
  server may reject or correct it later. No confirmation or retraction event
  follows a prediction.
- Fields whose value the client does not know are present with value `null`.
  `null` never means zero or "none".
- Events never carry `id`.

**Delivery and ordering.** Events are recorded on the client thread while a
world is loaded and written to every subscribed connection immediately. Nothing
is recorded or replayed outside a world, before a session subscribes, or while
it is disconnected. Each connection receives one ordered stream: events,
observations, and replies produced on the client thread (`inventory_result`,
`scan_result`, apply-time `error`) appear in the order the client thread produced them.
Therefore an event with tick T arrives after every observation with tick less
than T and before every observation with tick T or greater. The observation
for tick T, if this connection is due one, already reflects the event as far as
client state shows it. A coalesced observation older than an event is
discarded rather than delivered after it (it counts as coalesced). Errors that
the network thread produces while parsing a frame (`invalid_json`,
`invalid_field`, `role_forbidden`, ...) are not ordered relative to events.
Events never answer requests: an agent waiting for a reply keeps matching it by
`type` and `id`, and must not treat any event as an acknowledgment.

**No exactly-once across reconnects.** Within one connection, each event is
delivered at most once and in order, without gaps. Across a disconnect, events
that occur while no subscribed connection exists are lost, and events that were
written but not yet read are lost with the connection. Reconnecting never
replays them. `worldSession` and `tick` let an agent place a new stream relative
to an old one; `seq` cannot.

**Overflow.** Event delivery has its own per-connection bound, separate from
observation coalescing: at most 1024 events written but not yet accepted by the
operating-system socket. Events also count toward the shared 256 KiB
reliable-output byte budget. The bound limits bursts as well as slow readers:
over a thousand events within a few milliseconds can overflow even a reader
that keeps up on average. Events are never coalesced, dropped or reordered
to stay within the bound. When a new event would exceed either limit, the mod
closes only that connection: a best-effort `overloaded` error, then close code
1013 with reason `event overflow`. The overflowing event and all later events
are not delivered to it. A saturated connection may close without delivering
the error or close frame. The last `seq` the agent received marks where its
stream ended. Overflow of a controller connection is controller loss, so the
normal release-all safety rule applies. Other connections are unaffected.

Text fields (`message`, `text`) are limited to 2048 UTF-16 characters. Longer
text is cut and the event carries `truncated: true`. Those events always carry
`truncated`.

#### Event taxonomy

| `event` | `basis` | Fields |
|---|---|---|
| `damage` | `server` | `source`, `amount`, `health` |
| `death` | `server` | `message`, `truncated` |
| `respawn` | `server` | `dimension` |
| `dimension_change` | `server` | `from`, `to` |
| `item_pickup` | `server` | `item`, `count` |
| `chat` | `server` | `kind`, `text`, `sender`, `chatType`, `truncated` |
| `block_broken` | `client` | `block`, `pos` |

```json
{"type":"event","event":"damage","seq":1,"worldSession":"5d0c6f3e9a4b2c18","tick":120,"basis":"server","source":{"type":"minecraft:mob_attack","attacker":"minecraft:zombie","direct":"minecraft:zombie"},"amount":2.5,"health":17.5}
{"type":"event","event":"death","seq":2,"worldSession":"5d0c6f3e9a4b2c18","tick":300,"basis":"server","message":"Player fell out of the world","truncated":false}
{"type":"event","event":"respawn","seq":3,"worldSession":"5d0c6f3e9a4b2c18","tick":302,"basis":"server","dimension":"minecraft:overworld"}
{"type":"event","event":"dimension_change","seq":4,"worldSession":"5d0c6f3e9a4b2c18","tick":410,"basis":"server","from":"minecraft:overworld","to":"minecraft:the_nether"}
{"type":"event","event":"item_pickup","seq":5,"worldSession":"5d0c6f3e9a4b2c18","tick":455,"basis":"server","item":"minecraft:diamond","count":3}
{"type":"event","event":"chat","seq":6,"worldSession":"5d0c6f3e9a4b2c18","tick":460,"basis":"server","kind":"system","text":"Hello","sender":null,"chatType":null,"truncated":false}
{"type":"event","event":"block_broken","seq":7,"worldSession":"5d0c6f3e9a4b2c18","tick":470,"basis":"client","block":"minecraft:glass","pos":{"x":0,"y":-59,"z":3}}
```

- **`damage`** — the local player lost health. The server reports the damage
  source and, separately, synchronizes the resulting health; the mod pairs them.
  - `source`: object, or `null` when health fell without a damage report.
    `type` is the damage type id. `attacker` is the entity type id of the
    responsible entity, and `direct` the entity type id of the entity that
    directly dealt the damage; either is `null` when there is none or the
    client does not know it.
  - `amount`: health points lost; `health`: the resulting health. Both come
    from server-synchronized health (the health update or entity data) as this
    client sees it, compared with the previous value for the same player.
    Both are `null` when no health loss is seen within 20 client ticks of the
    damage report, for example damage fully absorbed or a delayed update.
  - The event is recorded when the pairing completes: when the loss is seen, on
    death, or when the 20-tick window ends. If a second damage report arrives
    before the first is paired, the first is reported with `amount` `null`.
    A loss seen after its window, or without any report, is reported with
    `source` `null`. A player's first health update after joining or
    respawning is a baseline, never damage; healing is not reported.
  - Death reports any waiting report, and any health not yet seen lost, as
    `damage` before `death` (with `health` 0). A death that arrives without a
    damage report (observed for `/kill` in the Nether) reports `source` `null`. Health changes after death are not damage.
- **`death`** — the server reported the local player's death. `message` is the
  death message as plain text, or `null` when the server sent none.
- **`respawn`** — the server respawned the local player after death.
  `dimension` is the dimension respawned into.
- **`dimension_change`** — the local player moved to a different dimension
  (portal, command, or respawning elsewhere). A respawn that changes
  dimension reports `respawn` first, then `dimension_change`.
- **`item_pickup`** — the server reported that the local player collected an
  item entity. `item` is the item id and `count` the number collected. `item`
  is `null` if the client did not know the collected entity's item. Experience
  orbs are not item pickups. Items added in other ways, such as commands or
  crafting, are not pickups.
- **`chat`** — a chat or system message was shown to the player. `kind` is
  `"chat"` (player chat), `"system"`, or `"action_bar"` (a system message the
  server sent as overlay text; `/title` titles and action bars are a separate
  mechanism and are not reported). `text`
  is the displayed plain text. `sender` is the sender's profile UUID for player
  chat, otherwise `null`. `chatType` is the chat type id when the message has
  one (for example `minecraft:chat` or `minecraft:say_command`), otherwise
  `null`. Messages the client hides (blocked players, secure-chat-only
  filtering) or another mod suppresses are not reported. A message delayed by
  the vanilla chat-delay option is reported when it is shown.
  Messages the client generates locally are not reported.
- **`block_broken`** — the client predicted that the local player broke a
  block. `block` is the id of the block before breaking, `pos` its integer
  block position. This is a client prediction: the server may refuse the
  break (protection, latency) and restore the block, with no follow-up event.

### error — malformed or invalid input

```json
{"type": "error", "code": "invalid_field", "message": "field \"pitch\" must be a number",
 "id": 12, "input": "{\"type\":\"look\",\"id\":12,\"yaw\":0,\"pitch\":\"up\"}"}
```

- `code` — machine-readable, from the taxonomy below.
- `message` — human-readable explanation; wording is not part of the
  contract and may change without a version bump.
- `id` — echoed if the offending message carried a valid `id`.
- `input` — the offending raw frame text, truncated to 256 characters. Present only when a frame caused the error.
- `supported` — only on `unsupported_version`: array of protocol versions
  the mod speaks.
- `reason` — with `inventoryStorage`, on `inventory_unavailable`,
  `inventory_impossible` and `inventory_cancelled` errors that answer an
  `inventory` request, and with `blockScan` on every `scan_refused` and
  `scan_cancelled` error: a machine-readable rejection reason (below). Absent
  on other errors.
- `limits` — only on `scan_refused` with reason `over_radius` or
  `over_volume`: `{"radius": …, "maxVolume": …}`, the caps in force.

## Safety behavior (normative)

- On disconnect, socket error, or the client leaving the world, **all
  controls release within one client tick**. The player idles; nothing
  stays held.
- The release-all rule applies to sessions that completed `hello`. A
  connection that never completed the handshake is not a controller; its
  close is not an agent loss.
- Loss of an **observer** connection is not an agent loss: it releases
  nothing, affects no held control, and does not disturb the controller.
  Only controller loss triggers the release-all rule.
- Malformed input never crashes the client and never alters held controls.

### Emergency release

The local rebindable panic key (default F8) releases movement, jump, sneak,
sprint, attack/use holds and taps, pending hotbar changes, camera smoothing,
and inventory animation, and severs the controller. Observers remain attached.
Completed hotbar selections or inventory clicks are not rolled back; inventory
cancellation uses the safe cursor recovery rules above. Panic works in screens
and while paused. World exit also severs the controller to prevent stale work
from driving a subsequently joined world.

**Panic latch (`panicLatch`).** Panic also latches agent control off. While
latched, every `controller` hello is refused; reconnecting does not restore
agent control. Pressing panic again, any number of times, only keeps the latch
engaged — panic never re-enables anything. A separate rebindable local
**re-arm** key ("Allow agent control", default F9, shown in the Controls menu
and handled only in game with no screen open) clears the latch. Re-arming only
permits a future controller hello; it grants, restores or replays nothing, and
a released input stays released until a newly admitted controller sends it.
The latch persists across world exit and rejoin. It is in-memory client state:
it resets when the Minecraft client restarts, which starts unlatched. Observer
admission and attached observers are unaffected by the latch, the sever and
re-arming. The client shows an unobtrusive local notice when control is
disabled, when panic is pressed again while latched, on joining a world while
latched, and when re-armed.

Consumers distinguish these outcomes with existing mechanisms:

| Outcome | What the agent receives |
|---|---|
| Panic severs an attached controller | Close 1008, reason `local panic`; no error frame |
| Controller hello while latched (including one racing the panic) | `error` code `panic_latched` as the final text frame, then close 1008 with reason `panic_latched`; the hello is never admitted |
| Another controller is attached | `error` code `controller_attached`, close 1013 |
| Liveness watchdog | Close 1008, reason `pong timeout`; no error frame |
| Transport loss or game exit | No close frame (1006 locally) or close 1001 |

Admission and the latch are decided atomically: a controller hello is either
admitted before the panic and then severed with `local panic` (its `hello`
reply may not have been written yet, so the handshake can end with that close
alone) or refused with `panic_latched`. No controller is admitted while latched. A latched refusal is not a retryable capacity condition;
agents should stop reconnecting, or back off and surface the state, until the
human re-arms. An agent cannot detect re-arming except by a later successful
hello. Refused hellos are not agent loss and release nothing; panic already
released everything.

Controller loss/watchdog release runs at the next client tick or rendered frame,
whichever occurs first, before ordinary work. At 20 ticks/s with a responsive
client this is within 50 ms of loss detection; pong loss detection takes at most
configured timeout plus one watchdog interval (at most 1 second; 0.5 seconds at
the 2-second default, so at most 2.5 seconds after the last pong). No wall-clock
guarantee is possible while the Minecraft client thread itself is stalled.
